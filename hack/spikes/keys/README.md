# Step 5's spike: keys that expire

The step-5 plan's X-01, part 3, for its D5: a function's own key lasting 12 hours, renewed at half its life by a new key written into the function's environment Secret and its pods replaced one at a time, each new one ready before an old one goes.

```bash
hack/spikes/keys/sdks.sh       # what AWS's SDKs show past a key's end, under a minute once the SDKs are installed
hack/spikes/keys/rollout.sh    # a function's pods replaced under load, and what a rollout costs, about 4 minutes
```

`sdks.sh` starts `expired.mjs`, which answers every signed request as each service answers a key that has expired (S3's `ExpiredToken` in XML, SQS's `ExpiredToken` in its JSON protocol, SES's and Lambda's `ExpiredTokenException`), and has AWS's SDK for JavaScript (`sdks.mjs`) and boto3 (`sdks.py`) call S3, SQS, SES and Lambda there, the key in the environment as a function's pod has it; then again with `AWS_CREDENTIAL_EXPIRATION` set an hour ago, as a key's end could be given to them. Its results land in `hack/.spike-keys/sdks.md`.

`rollout.sh` makes a function through FF's API, on a stack of its own as L4's (`hack/lib/e2e-stack.sh`), kept at one instance, and calls it without pause from four callers (`load.mjs`) for 30 s through each of three paths in turn: FF's API; the cluster API's service proxy, as the backend calls in development; and the function's Service from a pod in `ff-system`, labeled as the backend's pods are, as the backend calls in production, with the backend's rule there (Node.js's default agent, which keeps connections alive, and a refused connection tried again for 5 s). 8 s in, the function's environment changes, which takes the path a renewed key will: a new Secret, then the rollout. Then the cluster API's requests during one rollout, from its metrics (`api_requests.py`), against a quiet window as long. Its results land in `hack/.spike-keys/rollout.md`.

## What it found, on 2026-10-31

With AWS's SDK for JavaScript 3.1156.0 and boto3 1.43.118; on the k3d dev cluster (k3s 1.37.1), FF's Node.js runtime:

1. **Past its key's end, each SDK shows the service's own refusal, and doesn't try again:** one request each, for both SDKs and all four services. The SDK for JavaScript throws `ExpiredToken` for S3 (400) and SQS (403, from SQS's `x-amzn-query-error`), `ExpiredTokenException` for SES and Lambda (403), with the message as sent; boto3 raises a `ClientError` with the same codes and no retry. So "refused saying it expired, in each service's words" is what a function's code will see, at once.
2. **`AWS_CREDENTIAL_EXPIRATION` must not be given:** with it set an hour ago, the SDK for JavaScript sends its requests as before, but boto3 sends none and raises `RuntimeError: Credentials were refreshed, but the refreshed credentials are still expired.`, a message that names no service and no key. botocore refreshes credentials that have an expiration from 15 minutes before it, and fails from 10 minutes before, so it would fail before the key does, rereading an environment that can't change in a running process. D5 gives the same variables as today, and none for the key's end: right.
3. **Replaced under load, production's path loses calls, development's loses none.** Through FF's API and through the cluster API's proxy, none of 573 and 587 calls failed: the proxy picks a ready pod at each request, and the old pod had none once it was told to stop. Straight to the Service, as the backend calls in production, 166 of 742 calls failed: the backend's connections, kept alive, went on reaching the old pod after its SIGTERM, a Service's routing applying to new connections alone, and the runtime answers every call that reaches it once it is stopping with `503 ServiceUnavailableException: Runtime is shutting down`, 162 times in the 205 ms it took to finish the calls it had already taken (the load's callers asking again at once: a backend's callers lose each call sent in that time); then the 4 connections it closed as it went were reset under a call (`ECONNRESET`). One connection refused was tried again and answered, as the backend's rule means. The window grows with the function's calls: a function whose calls take seconds refuses for seconds. So every rollout in production loses calls today, a deploy's as much as a renewal's: the runtimes, both answering 503 so, must serve what reaches them while they drain, and the backend must try again a call whose kept-alive connection was closed before it was read. A renewal every 6 hours makes that four rollouts a day for each warm function.
4. **A rollout of one instance takes 4 to 6 s, its change answered as it ends:** FF answered the change after 4.1 to 6.1 s, once the new pod was serving; the old pod was gone 0.4 to 1.1 s later. The new environment answered from 3.4 to 5.5 s after the change began, the old one until then.
5. **What a rollout costs the cluster's API is small:** 91 requests in the 5.6 s of one change, against 6 in a quiet window as long: FF's 7 server-side applies (the namespace, its quota, its limits, its network policy, the Service, the Secret and the Deployment) and the old Secret's deletion; 7 reads of the Deployment and 17 of pods, FF's as it waits for the rollout among them; and the controllers' and the kubelet's writes (the ReplicaSets, the pods and their status, the endpoints, 12 events). A hundred warm functions renewed every 6 hours make 17 rollouts an hour: 17 Secrets written and 17 deleted, 17 pods started, and about 1,400 requests, one every 2.5 s. A renewal needs only the Secret and the Deployment: the other five applies are each deploy's, which a renewal can leave out.

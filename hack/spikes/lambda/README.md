# Step 5's spike: what AWS's tools call on Lambda's API

The step-5 plan's X-01, part 1. `lambda-endpoint.mjs` is a minimal Lambda endpoint, Node.js's standard library alone: Lambda's REST API at its dated paths, Signature Version 4 for the service `lambda`, the 41 operations of the plan's D2 kept in memory, and every other operation refused in Lambda's error shape, saying it comes later. A function is `Pending` for 3 s after it is made and an update `InProgress` for 2 s, as Lambda's are, so that the clients' waiters poll. It records every request. `run.sh` starts one, fresh, for each client, and takes the client through a function's whole life: made, waited for, called (with its log's tail, and asynchronously), its code (6 MB) and settings changed, published, aliased and called by its alias and its alias's ARN, given a URL, a permission, an SQS mapping, async settings, a concurrency and tags, read in every way, refused once for an operation that comes later and once for a function that doesn't exist, and deleted. `analyze.py` reads the recordings.

```bash
hack/spikes/lambda/run.sh               # the AWS CLI, AWS's SDK for JavaScript and boto3, about 3 minutes
hack/spikes/lambda/run.sh sdk boto3     # some of them
```

Each client's steps and requests stay in `hack/.spike-lambda/` (`<client>.steps.jsonl`, `<client>.requests.jsonl`), with `summary.md`.

## What it found, on 2026-10-31

The AWS CLI 2.34.32 (`amazon/aws-cli`), AWS's SDK for JavaScript v3 (`@aws-sdk/client-lambda` 3.1156.0, which says `aws-sdk-js/3.1155.0`) and boto3 1.43.118 (with botocore 1.43.123, the newest its pin allows: a later spike pins botocore too), each with only the endpoint, the region and a key:

1. **Every step went through,** but for the five refusals the flow asks for, in all three: 30 of 30 steps for the SDK and boto3, 51 for the CLI, whose reads are a command each; 58, 58 and 52 requests. They called D2's operations and no other.
2. **Paths are signed as every service but S3 signs them:** each segment escaped again, in all 168 requests. An ARN in a path (invoking by an alias's ARN, the tags' operations) is sent escaped, `arn%3Aaws%3Alambda…`, and signed over `arn%253Aaws%253Alambda…`: the plan's D3, one signature check with each service's rule, holds for Lambda with SES's rule.
3. **What is signed differs:** the SDK for JavaScript signs `host`, `x-amz-date`, `x-amz-content-sha256`, which it sends, and its own `amz-sdk-invocation-id`, `amz-sdk-request` and `x-amz-user-agent`, with `content-length` and `content-type` when there is a body; boto3 and the CLI sign `host` and `x-amz-date` alone, `content-type` with a body, and send no `x-amz-content-sha256`. A front door takes the payload's hash from that header when there is one and from the body when there isn't, and checks the headers each client names, whatever they are; `x-amz-log-type`, when asked, is signed by all three.
4. **The waiters poll `GetFunction`,** never `GetFunctionConfiguration`, until `State` is `Active` (`function-active-v2`) or `LastUpdateStatus` is `Successful` (`function-updated-v2`): boto3 every 1.0 s, as botocore's model has it (300 tries, so it gives up after 5 minutes); the SDK for JavaScript from 1 s, backing off with jitter (1.0 to 2.0 s here), until the `maxWaitTime` its caller gives; the CLI as boto3, but each of its commands takes a container's start, so it polled once or twice. A function `Pending` for seconds, as FF's is while its pod starts, costs a poll a second: GetFunction must be cheap.
5. **A call while the function is `Pending`, or an update while one is `InProgress`, is refused `409 ResourceConflictException`,** and none of the three retries it: the caller waits (the waiters) and asks again. FF must refuse the same way, not queue the call: Terraform's provider, which retries it, is part 1's next run.
6. **The later refusal, `400 UnknownOperationException`, is shown and not retried** by any of them: the SDK as `UnknownOperationException: FF doesn't offer this operation of Lambda's API yet: GET /2018-10-31/layers. It comes in a later step.`, from the header `x-amzn-ErrorType` and the body's `message`; boto3 as a `ClientError`, the type being in no model, `An error occurred (UnknownOperationException) when calling the ListLayers operation: …`; the CLI as `aws: [ERROR]: An error occurred (UnknownOperationException) when calling the ListLayers operation: …`. One request each.
7. **A missing function, `404 ResourceNotFoundException`,** is the SDK's and boto3's modeled exception of that name, with the message as sent (`Function not found: arn:aws:lambda:…`), and the CLI's same sentence.
8. **The largest body** is the code: a 6 MB zip is 8.4 MB of JSON (base64), sent by all three with a `Content-Length`, never chunked. Lambda takes 50 MB zipped in a request, about 67 MB of JSON: the front door's body limit is that, for these two operations only.
9. **Invoke:** the qualifier comes as `?Qualifier=live`, or inside the ARN in the path; `X-Amz-Log-Type: Tail` asks for `X-Amz-Log-Result`, the log's last 4 KB in base64, which all three decode; `X-Amz-Executed-Version` is read as `ExecutedVersion`; an asynchronous call is `X-Amz-Invocation-Type: Event`, answered `202` with no body.

# Step 5's spike: how a function's versions run

The step-5 plan's X-01, part 2. `run.sh` makes a function through FF's API, on a stack of its own as L4's (`hack/lib/e2e-stack.sh`) and the dev cluster, and beside its `$LATEST`, which FF makes, a version 1 made by hand from `$LATEST`'s Deployment and Service, as the plan has a version run: a Deployment `fn-<id>-v1` of its own, with a label `ff.dev/version` on it, on its pods and in its selector, `FUNCTION_VERSION` set to 1, and a Service of its own. It measures the version's first call from zero three times, and `$LATEST`'s through FF; calls `$LATEST`'s Service a hundred times with both versions up; reads both Deployments and FF's two counts of a function's instances; and routes a thousand calls as an alias with 10 % to version 1 would, each to its version's Service. `calls.mjs` makes the calls through the cluster API's service proxy, as FF's backend does, and counts which version answered each. Everything it made goes at the end; what it found lands in `hack/.spike-versions/results.md`.

```bash
hack/spikes/versions/run.sh      # about 2 minutes, the backend's build included
```

## What it found, on 2026-10-31

On the k3d dev cluster (k3s 1.37.1), with FF's Node.js runtime:

1. **A version's first call from zero costs what `$LATEST`'s costs, a pod's start.** Scaled from zero to one, version 1's pod was ready after 5.2, 4.7 and 4.0 s, and answered 16 ms later each time; `$LATEST` from zero through FF answered after 6.1 s, FF's own wait and its API included. None of the three first calls was refused: by the time the Deployment counted the pod ready, the cluster API's proxy had it among its Service's endpoints. A version made at its first call and scaled to zero when idle, as the plan has it, costs its first caller what a cold `$LATEST` costs today.
2. **`$LATEST`'s Service takes the version's pods for its own.** It selects by `ff.dev/function-id` alone, which the version's pods carry too: 43 of 100 calls to `$LATEST` were answered by version 1. Its Deployment doesn't take them, since each ReplicaSet owns the pods of its own template's hash: each Deployment kept its one pod. So every version's Service selects a version label beside the function's ID, `$LATEST`'s too: `ff.dev/version`, `latest` for `$LATEST`, since a label's value can't hold `$`. A Deployment's selector can't change, and needn't: `$LATEST`'s keeps its own. But its pods need the label, and adding it to their template rolls them, as here; so the label goes on the pods first and into the Service's selector after, or the Service has no pod while they roll. The pods keep `ff.dev/function-id`: the log pipeline gives each line to its function by that label (`deploy/k8s/logging/fluent-bit/ff.lua`), and without it by the pod's name, which for a version's pod would read `<id>-v1`.
3. **FF counts one Deployment's instances.** With both versions up, two pods were ready, and both of FF's counts said one: `readyInstances`, which the metrics and the idle sweep read, reads `$LATEST`'s Deployment by its name, and `readyInstancesByFunction`, which the capacity's count reads, keeps the last Deployment listed for each function ID. Listing the function's Deployments by its label counts two. So `maxInstances` caps a sum: the counts, the scaler (which raises `$LATEST`'s Deployment by its name, at a cold start and for a burst) and the idle sweep read every Deployment of the function by its label.
4. **An alias's share is the caller's choice, at each call.** Routed as an alias with 10 % to version 1 would be, each call to its version's Service through the same proxy, 107 of 1,000 calls went to version 1 (from 76 to 124 is chance's 99 % around 100), each was answered by the version it was sent to, and none failed. With a Service for each version, the backend picks the version by the alias's weights at each call, and nothing in the cluster changes when the weights do. Through the proxy, a call took 1.6 ms at the median and 52 ms at the 95th percentile.
5. **Read in the code, not run here, since the spike's function had no environment:** a function's environment is kept in two Secrets, `fn-<id>-env-0` and `fn-<id>-env-1`, written in turn, a new environment going into the one `$LATEST`'s running pods don't read. A version's Deployment copied from `$LATEST`'s reads the Secret `$LATEST` read then, which `$LATEST`'s second change of environment after it overwrites: the version's pods started after that would run with `$LATEST`'s newer environment. A version needs a Secret of its own, written once, when it is published. Its code is safe as it is: the Deployment names its code's image by reference (the `code` volume), which the copy keeps.

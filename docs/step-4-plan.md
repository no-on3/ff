## 2. Goals and non-goals

**Goals:**

1. **A static site:** a built folder at `https://<bucket>.site.<domain>/`, or at the customer's own domain with TLS, updated by one command, as S3's website hosting behind CloudFront serves one; a single-page app's routes answered by its `index.html`.
2. **E-mail from apps:** SES v2's `SendEmail` through AWS's SDKs with only the endpoint changed, from a domain the account proved (DKIM and SPF), within quotas that start small and grow; bounces and complaints kept out by a suppression list; and the account's switch in the admin app.
3. **A cache:** a Valkey database for the account, its address and password shown once, reached by the account's functions whatever their internet access, its memory the plan's, billed by the hour, as ElastiCache bills a node.

**Non-goals:** pages made on the server (always-on services, What to build next §9.1); a network of caches abroad, as CloudFront has; receiving mail, beyond the bounces; marketing tools (lists, template editors); Valkey's cluster mode and modules; SES's events to topics (SNS comes later); FF's own counters in Valkey.

## 3. Decisions

§9's choices, taken as recommended; where W-01's spikes or the building change a decision, the decision says so.

### D1. A site is a bucket with S3's website configuration
- S3's `PutBucketWebsite`, `GetBucketWebsite` and `DeleteBucketWebsite`, at the S3 front door in S3's XML and in FF's API in its JSON names: the index document (`index.html`), the error document (`404.html`), and one setting of FF's, as CloudFront's custom error responses give it: an unknown path answers the index document with 200, for single-page apps. Routing rules and redirects: later.
- Files go up as to any bucket: `aws s3 sync ./dist s3://<bucket>`, or `ff sites deploy ./dist`, which syncs, deletes what is gone, and sets each file's content type and cache header by its name: a year and `immutable` for hashed assets, `no-cache` for HTML, as FF's console has them.
- A bucket with a website configuration is public to read at its website address alone; its S3 API stays signed. No bucket policies or ACLs: the website configuration is the public switch, as S3's public-read policy with "Block public access" off would be.
- **Why:** S3's shape keeps the way out (S3 and CloudFront), and reuses buckets with their measures, limits and bills. A site with deploys and rollbacks, as Amplify Hosting or Netlify have, can come later on top.
- **As built (W-02, part 1):** a bucket's website configuration in a column of its own (the migration `BucketWebsites`): S3's `PutBucketWebsite`, `GetBucketWebsite` and `DeleteBucketWebsite` at the S3 front door, in S3's XML, read by the front door's own reader, counted as a PUT, a GET and a free DELETE; and `PUT`, `GET`, `DELETE /buckets/:name/website` in FF's API, in S3's JSON names (`indexDocument.suffix`, `errorDocument.key`) and FF's `singlePageApp`, which S3's XML can't say: `PutBucketWebsite` keeps it as it was. S3's refusals in its words (an index document with a slash, none at all, names past 1,024 characters, the XML malformed); redirects and routing rules answer `NotImplemented`, saying they come later. A read-only key changes nothing; the audit log's `bucket.website`, an SDK's change under its access key. A bucket's view gains `siteUrl`, the console's mirror of it too, and the admin app's account page says which buckets are public sites. The sites' address is `FF_WEBSITE_BASE` (`https://site.<domain>`; `http://site.localhost:3004` in development), https in production.
- **As built (W-03, part 2):** `ff sites deploy <bucket> <folder>` asks the API for a deploy's own key (`POST /buckets/:name/website/deploy-keys`: the bucket alone, read-write, for an hour, any owner or developer, an API key too, never listed or counted with the account's two keys; the migration `DeployKeys`), lists the bucket, uploads the files whose MD5 isn't the stored ETag, assets first and pages last, each typed by its name from the same table as the website server's and cached a year (`immutable`) when its name carries a hash, `no-cache` otherwise; deletes the bucket's files the folder hasn't (unless `--keep`), revokes the key, and makes the bucket a site when it isn't one (`--spa`, `--index-document`, `--error-document`, the folder's `404.html` taken by default). Signed by `ff` itself (SigV4, S3's rules, MD5 of its own), with no AWS CLI needed. `ff sites get|remove`, and the console's site panel on a bucket's page: its address, its settings, the deploy command and the AWS CLI's, its visits in the last day, its domains.

### D2. The website server: the backend's fourth front door
- A server of the backend's own on a port of its own (`FF_WEBSITE_PORT`), behind the edge: `GET` and `HEAD` only; a folder's path answered by its index document; the error document with its status; `ETag` and `Last-Modified`, with 304; ranges; the content type stored, else by the file's name; `X-Content-Type-Options: nosniff`; no cookies.
- Requests counted as a bucket's GETs (S3's second class) and their bytes out, as the S3 front door counts them.
- **Why not Caddy's file server:** the files are in the S3 store under FF's names, which Caddy would need a module to read; the backend already reads the store, checks the account, and counts.
- **Measured by W-01's spike** ([ADR 0011](adr/0011-static-sites.md)): a site's first load as fast through the server as from the store. **Changed by it:** the store types an object written without a type from its bytes, so the S3 front door stores it as S3 does, `binary/octet-stream`, which the website server types by the file's name.
- **As built (W-02, part 2):** `WebsiteServer`, on `FF_WEBSITE_PORT` (3004; 0 for none), answering `<bucket>.<the sites' host>`, and the bucket a caller names, for a customer's own domain the function URL gateway will hand over (W-03). GET and HEAD; anything else 405 with `Allow`. A folder's path answers its index document; a folder named without its slash is redirected to it, 302, its query kept, when it has one, as S3's website endpoint does; a path with no file answers the error document with 404, or, a single-page app's, the index document with 200, else S3's own HTML error page (`NoSuchKey` and the key). The browser's `If-None-Match`, `If-Modified-Since`, `If-Match`, `If-Unmodified-Since` and `Range` go to the store, which answers 304, 206, 412 and 416 itself, its `ETag` and `Last-Modified` passed on; the type a file was uploaded with, else one by its name (`content-types.ts`, which `ff sites deploy` will share); `X-Content-Type-Options: nosniff` on every answer; no cookie. A path with a `.` or `..` segment, however escaped, or a control character, answers 400 `InvalidURI` without asking the store, so that no key outside the bucket is ever asked. A suspended account's sites, and those whose storage FF turned off, answer 403; without credit they answer, as reads do. Each visit counts in its bucket's minute in a class of its own, `website` (the migration `SiteTransfer`), which the hourly rating, the statement and `GET /usage` bill as S3's second class, and which the plan's monthly limit reads.

### D3. Addresses and certificates
- `https://<bucket>.site.<domain>/`: buckets' names are unique across FF and without dots, so each makes a host. A wildcard certificate for `*.site.<domain>` once FF's DNS allows it (decision 17), else one per site on demand.
- A customer's own domain, proved as a function URL's is, its certificate on demand: `custom_domains` gains a target kind (a function URL or a site), one `customDomains` limit for both.
- **As built (W-03, part 1):** a customer's domain names a function or a bucket (`custom_domains.bucket_id`, the migration `SiteDomains`, one of the two set), `/buckets/:name/website/domains` as `/functions/:id/url/domains` are, the plan's `customDomains` counting both; a domain under FF's own sites' host refused. The function URL gateway hands a verified site's domain to the website server, while its bucket is a site; the edge's `/tls/allowed` says yes to it and to `<bucket>.site.<domain>` for a bucket that is a site, no to any other. The edge answers `*.site.<domain>` (`FF_WEBSITE_DOMAIN`) with the website server's port, its certificates on demand; the manifests, the development server's Caddy and smoke test, L4 and the platform's end-to-end suite visit a site at its host and at a customer's domain.

### D4. E-mail from apps, with SES v2's API
- An endpoint of the backend's own on a port of its own, SES v2's REST API in JSON, signed with Signature Version 4 for the service `ses`, so that `@aws-sdk/client-sesv2` and boto3's `sesv2` work with the endpoint changed (`AWS_ENDPOINT_URL_SESV2`, which W-01's spike checks for each SDK).
- First: `CreateEmailIdentity` for a domain (FF makes its DKIM keys, as SES's "bring your own DKIM" takes them, and gives the records to publish), `GetEmailIdentity`, `ListEmailIdentities`, `DeleteEmailIdentity`, `SendEmail` (simple and raw content, 50 recipients at most), `GetAccount` (the quotas and the sandbox), and the suppression list's operations; the others answer `NotImplemented`. The account's keys and functions' own reach it, as they reach buckets and queues.
- SES's SMTP interface, with a password made from a key as SES makes it: later (§9, 5).
- **Measured by W-01's spike** ([ADR 0012](adr/0012-customer-mail.md)): AWS's three clients work with the endpoint changed alone. **Changed by it:** every client signs the path escaped twice, as for every service but S3, so FF's signature check takes a mode for it; today's SDKs list identities with `POST /v2/email/list-identities`, older ones with `GET /v2/email/identities`, and the endpoint answers both.
- **As built (W-06, part 1, the endpoint):** a server of the backend's on `FF_SES_PORT` (3005), behind the edge at `email.<domain>` (`FF_SES_BASE`, a customer's `AWS_ENDPOINT_URL_SESV2`): SES v2's REST API in JSON, Signature Version 4 for `ses`, the path escaped twice; the account's own keys that reach the whole account (one that names buckets or queues reaches those alone, as at the other two front doors), a read-only one only reading, and functions' own, whose pods get `AWS_ENDPOINT_URL_SESV2`, a name a function can't set; the account active. Each answer names its request (`x-amzn-RequestId`), each refusal its error (`x-amzn-ErrorType`) in SES's words. `SendEmail` answers `NotImplemented` until W-07 sends; so does every operation FF doesn't answer.
- **As built (W-06, part 2, identities):** `CreateEmailIdentity`, `GetEmailIdentity`, `ListEmailIdentities` (both ways), `DeleteEmailIdentity`; a domain gets an RSA key of 2,048 bits, FF's, sealed as secrets are, under a selector `ff` and 8 hexadecimal characters, as SES's own DKIM brought in (`SigningAttributesOrigin` `EXTERNAL`), and four records to publish: the key's TXT, its return path's (`bounces.mail.<domain>`) MX and SPF to the server of customers' mail (`FF_EMAIL_MAIL_HOST`), and a DMARC policy that only reports. Looked up every minute for 72 hours, then `FAILED`; once proved, once a day, `TEMPORARY_FAILURE` while its record is gone; its return path proved once its MX is found, its bounces until then FF's own (`FF_EMAIL_BOUNCE_DOMAIN`); asked through `FF_DOMAIN_RESOLVERS`, as customers' own domains are. An address is proved by the link FF e-mails it through its own mail, once, `<endpoint>/verify?token=…`, which answers a page in French and English. `GetAccount` (the plan's quotas, the sandbox) and the suppression list's four operations. FF's API: `/email/identities`, `/email/suppressions`, `GET /email/account`; the scopes `email:read` and `email:write`; `email.identity.create|verify|delete` and `email.suppression.put|delete` in the account's audit log.

### D5. The server that sends customers' mail
- Never FF's own relay: customers' mail goes out from an address and a return-path domain of their own (`bounces.mail.<domain>`), so that one customer's spam can't stop FF's mail.
- Recommended (§9, 6): the backend signs each message with the customer's DKIM key and hands it to a Postfix on a server and IP of its own, which delivers it and gets the bounces back. Postal, which the parent plan names, does more, with more to run; a local relay works if one signs each customer's domain.
- Queued in step 3's queue, as asynchronous calls are, so that a send is answered at once and retried when a server refuses for now.

### D6. Reputation: proven domains, a sandbox, quotas, a suppression list
- A sender's domain must be the account's, proved by its DKIM records, which FF checks as it checks a custom domain; SPF and DMARC advised in the records FF gives.
- **The sandbox, as SES's:** a new account sends only to addresses it proved (a link FF e-mails), 200 a day; an operator lifts it in the admin app, once the account says what it sends.
- **Quotas, as SES's:** messages a day and a second, from the plan, raised for an account as its age and payments grow, as its internet access may differ from its plan's.
- **Bounces and complaints:** a hard bounce or a complaint puts the address on the account's suppression list, as SES's; past SES's rates (5% of bounces, 0.1% of complaints) the account is reviewed, past 10% and 0.5% its sending stops and the operator is told.
- **Port 25 closed to every function,** whatever its internet access, so that no code sends around the quotas.
- The admin app's switch: an account's sending on or off.

### D7. A cache: a Valkey process for each, on a server of customers' caches
- Each cache is a Valkey process of its own, its memory the plan's (`maxmemory`, `allkeys-lru`), no persistence, TLS and a password; on a server apart from the cluster, as customers' databases are. One server with a user per account would cost less, but Valkey's users limit keys and commands, not memory: one account could fill it for all (§9, 8).
- Its address, `rediss://…`, shown once and kept by nobody, set as a function's secret (`ff caches create sessions --secret-for <function>`), as `ff db create` does; reached by the account's functions whatever their internet access, and from developers' machines.
- Measured each hour (its memory used, its connections) and billed by the hour of its size, as ElastiCache bills a node.
- **Measured by W-01's spike** ([ADR 0013](adr/0013-caches.md)): a cache answers over TLS about 2 s after its process starts, costs about 15 MB beside its `maxmemory`, and stays within it when filled past it; the customer's user refused every command that would change the server, an agent's user of FF's turning it off and on. No decision changed.
- **As built (W-04, part 1):** `deploy/cache/`: Valkey 9.1.2 and FF's agent (`agent.mjs`, Node.js's standard library alone), which keeps each cache's description on disk, writes its settings (TLS alone on its port, the plan's `maxmemory` with `allkeys-lru`, nothing on disk, `DEBUG` and `MODULE` off) and its ACL file (the customer's user, `default`, by its password's SHA-256, every command but those that would change the server; FF's own, `ff-agent`, which reads `INFO` and turns the customer off and on, never a key), starts its process under a user of its own and again when it stops, and answers the backend on port 6390, over HTTPS, to a token whose SHA-256 alone it has. docker-compose.yml's `cache` and `hack/k8s/cache-up.sh` in development; L2's, L4's and L5's servers of their own; `deploy/cache/README.md` says how to install it.
- **As built (W-04, part 2):** `/caches`: a name as ElastiCache names its clusters, the account's once; the first free port of the server's range (`FF_CACHE_PORTS`, 6400 to 6999); the plan's `caches` and `cacheMb` (D8); the address, `rediss://default:<password>@<host>:<port>`, in the answer that makes the cache or gives it a new password, and never again, FF keeping its SHA-256 alone; the connections under way keep theirs at a new password, as an ElastiCache AUTH token's rotation does. Functions reach the caches' ports whatever their account's internet access (one NetworkPolicy rule, a port range), and trust the server's CA with the database server's, in one file. A suspended or closed account's caches refuse its user and end its connections, their keys kept; reactivated, they let it in again; a closed account's are deleted at its data deletion date. `cache.create`, `cache.password` and `cache.delete` in the account's audit log.
- **As built (W-05, part 1):** the console's Caches page: each cache's address without its password, its memory used against the plan's and its connections, its last day's reads (`CacheHits` and `CacheMisses`) and keys let go; making one shows its address with its password once, with the `redis-cli` command and a form that sets it as a function's secret (`REDIS_URL` by default); a new password and a deletion are each asked first; "Add an alarm" opens the Alarms page on it. `ff caches create|list|get|password|delete`, `create` and `password` setting the address as a function's secret with `--secret-for <function>` (`--secret-name` names it), as `ff db create` does. The admin app's account page lists the account's caches, their memory used and connections, never their address.

### D8. Plans: new limits
- `websites` (none apart: a site is one of the account's buckets), `emailIdentities` (2 on beta), `emailsPerDay` and `emailsPerSecond` (the sandbox's 200 and 1 on beta), `caches` (1 on beta) and `cacheMb` (64 on beta). Each in the plan's schema, the admin app, the console and `ff account`.
- **As built (W-04):** `caches` (1 on beta) and `cacheMb` (64), the migration `Caches`, in the plan's schema, the admin app's plan editor, the console's account page and `ff account`.
- **As built (W-06):** `emailIdentities` (2 domains on beta; an address counts for none), `emailsPerDay` (200) and `emailsPerSecond` (1), the migration `EmailIdentities`, in the plan's schema, the admin app's plan editor, the console's account page and `ff account`.

### D9. Usage and billing
- Sites: S3's storage and requests, as today; their bytes out counted, not billed (decision 12), with a limit a month per plan (§9, 4).
- **As built (W-02, part 2):** the plan's `siteTransferGbPerMonth` (10 on beta; the migration `SiteTransfer`), in the admin app's plan editor, the console's account page and `ff account`. What an account's sites sent this month is read from their written minutes at most once a minute, with what the process sent since: past the limit, its sites answer 403, saying so, until the month's end; a limit passed a minute or two late, never early.
- E-mail as SES bills it: 0.10 US$ a thousand messages, each recipient one, and 0.12 US$ a GB of attachments, at the book's rate.
- Caches by the hour of their size, priced from ElastiCache for Valkey's nodes, at the book's rate.
- **As built (W-05, part 2):** every minute, under PostgreSQL's advisory lock, the backend measures each cache it hasn't measured yet in the hour (an active or suspended one, of an account that isn't closed) through the agent: its memory, the plan's, what its keys use, its connections, its hits, misses and evictions, and when its process started, into `cache_samples` (the migration `CacheMeasures`, by month, append-only). Each hour sampled is rated beside databases', buckets' and queues' (the kind `cache`): its memory for an hour, billed by the GB-hour at the book's `cacheGbHour`, ElastiCache for Valkey's `cache.t4g.micro` (0.0128 US$ an hour for 0.5 GiB, so 0.0256 a GB-hour) times the book's rate, with no free tier, as ElastiCache has none every month; an hour the server never answers in isn't billed. The migration gives every book not started yet the SKU and copies the book valid next month with it from that month's first hour. `GET /usage` and its CSV, the console's Usage page, `ff usage`, the statement and its PDF ("Cache | Heures | Go-heures | Montant HT"), the admin app's price editor and the reconciliation count them.

### D10. Suspension, credit and closure
- Suspended: its sites answer `AccessDenied`, its mail is refused, its caches' users are turned off. Without credit: sites still answer (reads go on, decision 13), caches go on, as databases do, and sending waits for credit. Closed: all three go with the account's data, at its deletion date.

### D11. Metrics and alarms
- Sites, as CloudFront names them: `Requests`, `BytesDownloaded`, `4xxErrorRate`, `5xxErrorRate`. Mail, as SES's: `Send`, `Delivery`, `Bounce`, `Complaint`, `Reject`, and the two reputation rates. Caches, as ElastiCache's: `BytesUsedForCache`, `CurrConnections`, `CacheHits`, `CacheMisses`, `Evictions`. Alarms on all of them, as on functions', buckets' and queues'.
- **As built (W-03, part 3):** `GET /buckets/:name/website/metrics`, from the website server's counts by the minute: `Requests` and `BytesDownloaded` (Sum), `4xxErrorRate`, `5xxErrorRate` and `TotalErrorRate` (Average, in percent, none in a period without a visit), as CloudFront names them; alarms on `Requests` and the three rates name the bucket, as a bucket's do; `ff sites metrics`, and the console's panel says the last day's visits. A bucket's own metrics count its site's visits among its requests.
- **As built (W-05, part 2):** `GET /caches/:name/metrics`, a point an hour from the samples: `BytesUsedForCache` and `CurrConnections` (Maximum, Average) as the hour's sample says; `CacheHits`, `CacheMisses` and `Evictions` (Sum), what happened in the hour, from the next hour's sample less its own, all of the next one's when the process started again between them (its start more than 5 s apart, or its counts gone down), none without the next hour's sample, as in the hour now. Alarms on all five name the cache (`cacheName`), judge hours, a day at most, and go with it; their e-mail names it, in both languages. The console's alarm form has the account's caches.

## 9. Choices made

**Taken as recommended on 2026-10-30** (the [decision log](decisions.md), 40 to 50), when you asked to build step 4 without stopping. Each with what it means and its recommendation:

1. **A site's shape:** S3's website hosting on a bucket, files sent with `aws s3 sync` or `ff sites deploy`, or a site of its own with deploys and rollbacks, as Netlify has. **Recommended: S3's,** the way out kept, the most reused; deploys can come on top.
2. **Single-page apps:** an unknown path answers `index.html` with 200, as CloudFront's custom error response does, or a 404 with the error document, as S3 alone does. **Recommended: a site's setting,** on when `ff sites deploy --spa` says so.
3. **Where sites live:** under FF's domain, `<bucket>.site.ffunc.cloud`, as function URLs live under `fn.ffunc.cloud`; or customers' content (sites and function URLs) on a domain of its own, as GitHub keeps `github.io` apart from `github.com`, so that a phishing page on one never marks FF's own domain. **Recommended: under `ffunc.cloud` now, as function URLs are,** and a domain of its own for customers' content before the public launch, a question added to the decision log.
4. **Bytes sites send out:** counted, not billed, as decision 12 says, with a limit a month per plan to protect the server; or billed now. **Recommended: counted with a limit,** 10 GB a month on beta.
5. **E-mail's interface:** SES v2's API first, SMTP later; or SMTP first, for code that sends with a library such as nodemailer. **Recommended: SES v2's API first:** AWS's SDKs work with the endpoint changed, and the quotas sit in one place.
6. **The server that sends:** a Postfix on a server and IP of its own, the backend signing with the customer's DKIM keys; Postal; or a local relay that signs each customer's domain, if one exists. **Recommended: Postfix with the backend's signing,** the fewest pieces, measured by W-01's spike.
7. **The sandbox and quotas, as SES's:** a new account sends only to addresses it proved, 200 a day, until an operator lifts it; or no sandbox, with quotas alone. **Recommended: the sandbox,** as SES has it.
8. **A cache's isolation:** a Valkey process for each, on a server of customers' caches; or one Valkey with a user per account, cheaper, its memory shared. **Recommended: a process for each.**
9. **A cache's persistence:** none, it is a cache; or snapshots. **Recommended: none,** said plainly in the docs.
10. **The order:** sites, then caches, then e-mail. **Recommended:** sites are the smallest and reuse the most; e-mail has the most risk, and waits on its server's IP.
11. **FF's own counters (its rate limits) in Valkey:** in this step, or once the backend runs more than one copy. **Recommended: later,** with the second copy, as the client-readiness plan says.

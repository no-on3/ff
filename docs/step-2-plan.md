## 2. Goals and non-goals

**Goals:**
- **AWS's shapes:** PostgreSQL itself, a major version RDS runs, so that `pg_dump` and a restore, or logical replication, move a database to RDS; the S3 API as AWS's SDKs and CLI speak it (SigV4, path-style and virtual-hosted addresses, AWS's XML errors), so that an S3 client works with only its endpoint changed, and a function's code with nothing changed (D8).
- **Isolation proven:** a database and its user per database, with no way into another's; buckets and keys per account; functions reach the database server and the S3 front door, and nothing else private; every route in the L5 suite.
- **Metered and billed as AWS bills:** storage by GB-month, sampled every hour; S3 requests by AWS's two classes; usage records written once; SKUs in the price book at AWS's list price on the book's date, with a free tier.
- **Limits that hold:** the plan's databases, storage and connections, its buckets and their storage and request rate, and what one customer can do to the others (§8).
- **Everything every new service needs** (What to build next §10): usage records, price, limits, console page and routes with the isolation test, admin page, backups, logs and metrics with alarms, documentation, a way out, abuse limits.

**Non-goals (for now):**
- **Bucket notifications** (step 3's queue, the parent's E-04 events), **public buckets and website hosting** (step 4's static sites), versioning, lifecycle rules, object lock, replication, ACLs and bucket policies beyond D7's keys, S3 Select, server access logs.
- **A server per account,** high availability beyond the server's own, read replicas, a connection pooler, extensions that aren't PostgreSQL's trusted ones, PostGIS (an operator may add it later, as RDS lists it).
- **DynamoDB,** as the parent plan decided (§6.7): FF recommends PostgreSQL.
- **The Lambda API and STS** beyond the credentials a function gets (D8): the parent's E-06 and E-07 in full come with step 5.

## 3. Decisions

[ADR 0008](adr/0008-customer-databases.md) records D1 to D5 and D12 to D14, and [ADR 0009](adr/0009-buckets.md) D6 to D9, as V-01's spike measured them on 2026-10-23; where the spike changed a decision, the decision below says so.

### D1. The customers' database server is the operator's, outside the cluster
- **A PostgreSQL server of its own,** apart from FF's: a customer's load or a full disk never reaches FF's control plane, its backups and restores are its own, and it can move to bigger hardware alone. One server to start; a server per plan tier when the plans need it, each database placed on one.
- **The newest major version RDS runs:** PostgreSQL 18 at the time of writing (19 comes out on 2026-11-19, and RDS has it in preview only). TLS required, `password_encryption = scram-sha-256`, its data on a disk of its own.
- **The backend holds an administrative role** on it, `CREATEDB` and `CREATEROLE` but not superuser, a member of `pg_read_all_stats` and `pg_signal_backend` (the spike), through new settings, separate as `DB_*` are rather than one URL, so that a password needs no encoding (V-02, as built): `FF_DATA_DB_HOST` as functions and customers reach it, `FF_DATA_DB_PORT`, `FF_DATA_DB_ADMIN_HOST` where the backend reaches it if elsewhere, `FF_DATA_DB_ADMIN_USER` and `FF_DATA_DB_ADMIN_PASSWORD`, `FF_DATA_DB_CIDRS` for D3, `FF_DATA_DB_CA_FILE` for D4's certificate. The server's own settings (`max_connections`, `temp_file_limit`, `log_*`, the trusted extensions) are the operator's, in a README of its own under `deploy/`.
- **In development:** a second PostgreSQL in `docker-compose.yml`, which the cluster's node reaches as `hack/k8s/app-database.sh` reaches its database, on a Docker network of its own.

### D2. A database and its user, with names nobody else learns
- **One user per database, its owner,** `NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS`, with the plan's connection limit (`CONNECTION LIMIT`). The user is granted to the backend's role `WITH INHERIT FALSE, SET TRUE`, which PostgreSQL 16 and later need for `CREATE DATABASE … OWNER`; what only the owner may do, the backend does as it, through `SET ROLE`: `REVOKE ALL ON DATABASE … FROM PUBLIC` (by the backend's role itself, it changed nothing, the spike found) and `DROP DATABASE`. The server's `pg_hba.conf` lets a user into its namesake database only (`hostssl sameuser`), the backend's role into the maintenance database only, and nothing without TLS.
- **Opaque names:** every user reads `pg_database` and `pg_roles`, so the database and its user are named `ff_` and 24 random characters, the same for both, never the account or the customer's name, which FF's own table keeps (`orders`).
- **The owner creates what it needs:** tables, schemas, and PostgreSQL's trusted extensions (`pgcrypto`, `citext`, `hstore`, `pg_trgm`, `uuid-ossp` and the others), which an owner may create without a superuser since PostgreSQL 13.

### D3. Functions reach the server, whatever the account's internet access
The tenant's NetworkPolicy gains a rule, written on every deploy as the rest is, and when the account makes a database: egress to `FF_DATA_DB_CIDRS` on port 5432 only. The server sees a function's connection come from the cluster's node, which masquerades what leaves it (the spike), and from the internet for D14. Between accounts, the wall is the user and its password: 32 random bytes, SCRAM, TLS.

### D4. The password: made by FF, shown once, given to functions as a secret
- **Made by the backend, shown once,** in the answer that creates the database or resets its password, as a connection string: FF keeps no copy. The backend sends the server a SCRAM verifier it computed itself (`ALTER ROLE … PASSWORD 'SCRAM-SHA-256$4096:…'`), so the password never reaches the server's logs either.
- **Into functions as their secret:** `ff db create orders --secret-for orders-api` sets `DATABASE_URL` on the functions named, through the existing secrets route, with the string it was given once; the console offers the same. A new password rolls the functions named out with it. FF stores no link between a database and functions.
- **The string:** `postgresql://<user>:<password>@<FF_DATA_DB_HOST>:5432/<db>?sslmode=require`. libpq's drivers encrypt with it, and node-postgres checks the certificate with it, as `verify-full` (the spike). So the server's certificate is for its name from a public CA in production, or from a CA of the operator's (development's too), which FF mounts in functions' pods and names in `NODE_EXTRA_CA_CERTS`, unless a function names its own, as AWS Lambda's Node.js runtime keeps RDS's CAs for that variable (ADR 0008, §9).

### D5. A database's size: measured every hour, signalled at the plan's limit, billed above it
PostgreSQL has no limit on a database's size, and an owner can turn any session setting back. So:
- **Every hour,** the backend samples each database's size (`pg_database_size`) and connections, which the bill and the metrics read.
- **At 80% and 100% of the plan's storage,** the owners are told. **Past 100%,** the database's new sessions start read-only (`ALTER ROLE <user> IN DATABASE <db> SET default_transaction_read_only = on`, which the backend's role may set; `ALTER DATABASE … SET` needs the owner, the spike found), and its sessions under way are ended so that a pool's come back read-only: an app sees it at its next write (SQLSTATE 25006), and a session may turn it off to delete what it no longer needs, or take the setting away, which the next hourly sample sets again. A signal, not a wall. As built (V-04): each minute, the backend measures every database not measured yet in the hour, so a new one within a minute, a closed account's not; the owners' e-mail goes through the account's notifications, once each time the database reaches a share, the highest when it reaches both at once; while it stays past, the hourly sample sets the signal again without ending the sessions under way; back under, the setting is reset; a reactivated account's databases start read-write, until their next sample.
- **The wall** is the server's disk alert to the operator, and the bill: what is above the plan's storage is billed by the GB-month, as RDS bills the storage it is given. A hard wall (a tablespace per database on a disk with quotas) needs a superuser and the operator's tooling: §9 kept the signal, confirmed on 2026-10-22.

### D6. Buckets behind FF's own S3 front door (the parent's E-04)
- **A small S3 server in the backend,** on a port of its own (as the function URL gateway is), at `s3.<domain>` and `<bucket>.s3.<domain>`. It checks each request's SigV4 signature, in a header or a presigned URL, with the account's keys; knows each bucket's account; counts each request by AWS's classes and its bytes; refuses past the plan's limits; and streams the request to the store with FF's own credentials, the bucket's name mapped to the store's.
- **Whatever store is behind it:** SeaweedFS in development, the operator's S3 in production. Customers' keys are never the store's, so its IAM, which differs from one store to another, doesn't matter; and step 3's notifications have their place here.
- **Checksums and presigned URLs, as S3 has them** (the spike): CRC-32, CRC-32C, CRC-64/NVME, SHA-1 and SHA-256, in a header or a trailer, checked by the front door before the upload completes; a presigned URL's checksum parameters signed and then ignored, as S3 does, since AWS's SDK for JavaScript signs the CRC-32 of an empty body into every presigned upload.
- **AWS's operations that apps use:** `PutObject`, `GetObject` with ranges, `HeadObject`, `DeleteObject`, `DeleteObjects`, `CopyObject`, `ListObjectsV2`, multipart upload (`Create`, `UploadPart`, `Complete`, `Abort`, `ListParts`), `HeadBucket`, `GetBucketLocation`, `ListBuckets` (the account's), and the streaming uploads with trailing checksums that AWS's SDKs send by default. Anything else answers `NotImplemented`, in AWS's words.
- **Buckets are made with FF's API,** the console and `ff`, which check the plan; `CreateBucket` through S3 comes later, with SAM and Terraform (CLI plan C-30, parent E-08).
- **Names are AWS's** (3 to 63 characters, lower-case letters, digits and hyphens; no dots, so that a virtual-hosted address keeps its certificate), unique across FF, as on AWS; free again once deleted.
- **As built (V-06):** the front door on `FF_STORAGE_PORT` (3002) at `FF_STORAGE_BASE`, in `BE/src/storage/`; a body streams to the store but for its last piece, which goes once the body's checks pass, so that the store never completes one that failed; the tables of buckets and keys came with it, since it can't be tested without them, and V-07 makes them through the API.

### D7. Keys: the account's own, at most two, shown once
An access key ID like AWS's (20 characters, `AKFF…`) and a secret of 40, shown once. The front door needs the secret itself to check signatures, so it is sealed with the key ring, as variables are. A key reaches all the account's buckets, or the ones it names, read-write or read-only. Two at most, so that one can replace the other, as IAM allows two per user.

### D8. Functions get credentials without a line of code (the parent's E-07, for S3)
Each function's pods get `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_REGION` and `AWS_ENDPOINT_URL_S3` in their Secret: a key of the function's own, made at its deploy, reaching its account's buckets, revoked when it is deleted. The endpoint is an IP address inside the cluster, which every SDK addresses path-style by itself (the spike), so no DNS name of FF's is needed there for buckets. AWS's SDKs read them, so `new S3Client({})` works on FF and, without them, on Lambda with its role. Short-lived session credentials, as Lambda's role gives, wait for the parent's STS-like work (step 5); §9 gave functions these keys meanwhile, confirmed on 2026-10-22. As built (V-08): with `AWS_DEFAULT_REGION` too, as Lambda sets it; the key made the first time a function is deployed, a function made before getting its own the next time an update rolls it out, one that works at most a function (a unique index), revoked before its record goes; in the environment's Secret beside its variables and secrets, and a new key a new version, its ID joining the environment's revision. The address is the backend's `FF_STORAGE_FUNCTION_ENDPOINT`, an IP address it checks: in production the Service `ff-storage`'s, fixed at `10.43.0.251:3002`, which every tenant's NetworkPolicy reaches at the backend's own pods (no `FF_STORAGE_FUNCTION_CIDRS`) and the backend's lets in on that port alone; in development, this machine at the gateway of the cluster's Docker network, its address in `FF_STORAGE_FUNCTION_CIDRS`. Without the setting, functions get no key. `AWS_ENDPOINT_URL_S3` is FF's to set, refused as a variable, in the console and `ff` too.

### D9. Usage and billing beyond functions
- **Usage records of their own,** written once: `database_samples` and `bucket_samples` (one row an hour each, size and count), and `storage_request_counts` (one row a minute per bucket and class, flushed by the front door: a request is never one row). Partitioned by month, as `usage_records` is. As built (V-04): `database_samples` keeps the database's name too, so that a deleted one keeps it on the bill. As built (V-06): `storage_request_counts` has a row per bucket, minute, class and writer, the backend process that counted them, so that two backends counting the same minute write two rows; with the bucket's name then, its GETs and PUTs, its 4xx and 5xx (CloudWatch's request metrics), and its bytes in and out; deletes and aborts in a third class, free.
- **The rating** gains rows per resource rather than per function (`usage_hourly`'s key widened, or a table beside it), and the statement a line per database and bucket; the reconciliation sums them too. As built (V-04): a table beside it, `resource_usage_hourly`, an hour of a database or a bucket per row (its kind, its name then, the book, its byte-hours, the hours sampled, S3's two classes of request); the statement a table per kind; the reconciliation the byte-hours both ways. GB-months are byte-hours over a GB and the month's hours, which have no finite decimal form (744 = 2³ × 3 × 31), so the quantity is rounded to twelve decimals and what it costs is exact, rounded once.
- **SKUs, optional in the book's schema,** priced 0 in the books from before: database storage per GB-month (RDS for PostgreSQL's gp3 storage), a monthly fee per database (0 unless §9 says otherwise), bucket storage per GB-month (S3 Standard's), and requests per 1,000 in AWS's two classes; each at AWS's us-east-1 list price on the new book's date, converted at the book's rate, as the first book was. A free tier for each (§9). As built (V-04): the new book starts at the first hour of the month after its migration runs, not at the next whole hour, so that databases are billed from a month's first day, which can be announced, and each month has one set of SKUs from its start; it copies the book valid then, with AWS's prices from its price lists read on 2026-10-23 (RDS's of 20 October, S3's of 15 October) at that book's rate, and gives the same SKUs to any book that hasn't started yet. Buckets' SKUs are in it already, for V-09. As built (V-09): `bucket_samples`, a row per bucket and hour, its listing's sizes summed and its objects counted, with its name then (each minute, an account with a bucket not measured in the hour has all its buckets measured, a closed account's not); each bucket's hour in `resource_usage_hourly` from its sample and that hour's request counts by S3's two classes, deletes free, a bucket asked only free requests having no row; the statement and its PDF a table of buckets (GB-months, each class's requests, the amount); the reconciliation buckets' byte-hours too, and their requests rated against those counted; `GET /usage` a `buckets` list, and its CSV a line per bucket with two columns for S3's classes.

### D10. Plans: new limits
`databases` (1 on the beta plan), `databaseStorageMb` (1,024), `databaseConnections` (10 per database); `buckets` (5), `bucketStorageMb` (5,120, AWS's free tier), `storageRequestsPerSecond` (100), `maxObjectMb` (5,120, as a single `PutObject` on S3). Each comes as the step-1 plan's D11 came: a migration, the schema, and the lists of the console, the admin app and the CLI. As built (V-07): `buckets` is counted under a lock on the account, as databases are; `storageRequestsPerSecond` in the throttler's storage, the account's keys together, `SlowDown` past it; `maxObjectMb` on a `PutObject`, a multipart upload's parts limited to S3's 5 GB each; `bucketStorageMb` is a signal, as databases' storage is, with V-09's hourly measures. As built (V-09): the account's buckets together, its owners told at 80% and 100% (the notification `bucket.storage`, in English or French); from 100%, uploads answer `AccountProblem`, saying why, while reads and deletes go on; an account whose buckets are full is measured every minute, so that room made lets its uploads in within a minute. The share told is kept on the account (`bucket_storage_notice`), which the front door reads with the account at each request.

### D11. Every way in is checked the same way
The database's own connections aside, every S3 request goes through the front door's checks in one place: the key, the account's status and credit, the plan's rate, the bucket's owner. A suspended account's keys and its functions' keys answer `AccountProblem`, as AWS's do for a suspended account. As built (V-07): the key's account active and its storage on, then the plan's requests a second, then the bucket's owner and the key's buckets, then, for an upload, the credit; each refusal in S3's words, and the reason with it.

### D12. Suspension, credit and closure
- **Suspended:** its databases' users can't log in, and their sessions end; its keys are refused. Reactivated, both come back.
- **Out of credit:** S3 writes answer `AccountProblem`, reads go on; databases go on, the usage billed later, as the parent plan's §8.1 keeps data for a long, contractual period. As built (V-07): uploads wait for credit (`PutObject`, `CopyObject`, a multipart upload's steps), while deletes go on with reads, as they lower the bill; the decision log's 13 named uploads.
- **Closed:** its databases are dropped and its buckets emptied and deleted with the rest of its data, at the data deletion date the retention already sets.

### D13. Backups and restores
- **The customers' server** gets WAL-G as FF's has: a base backup each night, point-in-time recovery to the second site, 7 days by default, RDS's default retention. One customer's database comes back by restoring the server to a scratch instance at the time asked, then copying that database into a new one of the account's: a runbook section, and the monthly drill does it. As built (V-05): a prefix and a key of its own at the second site; the scratch server reached over its socket only and archiving nothing, since its timeline would otherwise reach the second site beside the server's; the copy restored as the new database's user (`pg_restore --role`), so that no customer's password is needed.
- **Buckets** are not backed up by default: the store's own redundancy keeps them, as S3's does. Confirmed on 2026-10-22 (§9): the guide tells customers that there is no copy, and the question comes back before they keep important files on FF. As built (V-09): the guide's "Files in buckets", the page in French, the console's Buckets page and `ff buckets create` say it; the guide says what the store's redundancy doesn't cover (a file deleted or replaced by mistake, FF keeping no versions; the store lost) and how to keep a copy of one's own; the backups' README says it too.

### D14. Reaching the database from outside, and the way out
- **From a developer's machine:** the server's port is reachable from the internet, TLS only, as RDS's "publicly accessible" option, so that an owner runs `psql`, a migration tool or `pg_dump`; §9 kept it so rather than to functions only, confirmed on 2026-10-22.
- **The way out:** `pg_dump --format=custom` and `pg_restore` into RDS, or logical replication for a move without downtime: the export kit's `data/postgres.md`. As built (V-05): `pg_dump` and `pg_restore`, the writes stopped for the copy; logical replication needs users with `REPLICATION` and `wal_level = logical`, which the server doesn't give customers today, a question now in the [decision log](decisions.md). Buckets: `aws s3 sync` from FF's endpoint to a local folder, then to S3: its `data/s3-sync.sh`. As built (V-09): `cli/templates/export/data/s3-sync.sh`, both halves in one script, FF's variables dropped before the second, `--delete-gone` for what FF no longer has; `hack/cli-e2e.sh` runs it.

## 8. Risks

| Risk | Mitigation |
|---|---|
| One customer's heavy queries slow the others on the shared server | The plan's connection limit per database; the operator's monitoring of the server (its slowest statements, its connections, its disk); a server per plan tier when needed (D1) |
| A customer fills the server's disk | D5's samples and signal, the bill above the limit, the operator's disk alert; a hard wall if §9 says so |
| A database's or a user's name tells another customer something | Opaque names (D2); the customer's names stay in FF's table |
| The server exposed to the internet (D14) is attacked | TLS only, SCRAM, passwords of 32 random bytes, `pg_hba.conf` by database; §9 can keep it to functions only |
| The front door slows uploads, or holds memory | Streaming both ways, measured in V-01 against the store's own; its own process later if needed, as the URL gateway can (parent R-05) |
| An SDK's request the front door reads wrongly (chunked uploads, trailing checksums, a new default) | V-01's spike against three SDKs; L4 with each, run when their versions change |
| A key's secret must be readable to check signatures | Sealed with the key ring as variables are, never logged, never answered after creation |
| The new SKUs break the past price books, or the rating's per-function keys | Optional SKUs priced 0 in older books; the rating's tests over a month mixing functions and resources (V-04) |
| Restoring one database means restoring a whole server | The runbook's steps timed in the drill; RDS's own way is the same (a new instance from a point in time) |
| A plan's new key reaches an old backend during a rollout | The migration runs before the rollout, as for every limit so far; the new backend comes up with it |

Overview

You send code to the backend. The backend keeps the record in PostgreSQL and an archive copy in S3, then asks Kubernetes for your tenant's namespace and guardrails, a ConfigMap that holds the code, a Service, and a Deployment. Kubernetes starts a pod from the runtime image; the runtime loads your code once and reports ready. On each invocation the backend forwards your input to the pod, the runtime calls handler(event, context) in a worker, and the result travels back and is recorded with its duration. Idle functions are scaled to zero and start again on the next call. Click a component for details.

Data model

Three tables hold everything the backend knows. A function's invocations and metrics are deleted with it (ON DELETE CASCADE). The schema comes only from migrations (BE/src/migrations), in every environment: npm run migration:run applies them as a separate step, and the backend refuses to start while one is pending. Columns are snake_case in the database, while the API's JSON keeps camelCase (user_id is userId).

Not shown: the status values DELETED of functions and SUCCESS of function_invocations, which exist in the enums but are never set.

Inside the runtime

Every function pod runs one of two images, ff-runtime-nodejs:24-v2 or ff-runtime-python:3.13-v2, which speak the same protocol (version 2). Your code never runs in the main process: Node.js uses a worker thread with V8 heap limits, and Python a separate worker process with a memory budget. The main process therefore keeps answering probes, enforces the timeout, and replaces the worker after a timeout, an out-of-memory error, or a crash, without restarting the container. If that replacement can't load code that loaded before, the environment is broken, so the runtime exits and Kubernetes restarts the container. Your code runs in /var/task, as on Lambda.

What the runtime answers

HTTPerrorTypeWhen

Errors from an invocation carry x-ff-function-error: Unhandled. The backend records Sandbox.Timedout as an invocation with status TIMEOUT and every other error as ERROR, then answers the caller with 400 and "<errorType>: <message>"; a full queue answers 429 with TooManyRequestsException. A platform failure, such as an unreachable pod, answers 500 with a generic message and the request ID, and the history records it the same way; the details go only to the server log (D4 of the client-readiness plan). A call that gets no answer within the backend's own wait (see the limits below) is TIMEOUT too, with No response within … ms, in both invoke modes.

Isolation and limits

Each layer narrows what a tenant's code, or a compromised backend, can reach.

Kubernetes API: RBAC and an admission policy
The backend's ServiceAccount ff-system/ff-controller may manage only the objects functions need: no Secrets, no exec into pods, no changes to RBAC. The admission policy ff-controller-scope confines its writes, and its calls through a Service's proxy, to namespaces named ff-t-* and labelled app.kubernetes.io/managed-by=ff-controller. Only the development setup grants that proxy: in production the backend runs inside the cluster and calls the Services directly. Reads are cluster-wide, which the beta accepts under rules listed in deploy/k8s/README.md.

Pod Security restricted. A ResourceQuota (20 pods, 8 CPU, 8 Gi, 60 ConfigMaps, 30 Services), a LimitRange, and the NetworkPolicy ff-default-deny: ingress only from ff-system; egress only to DNS and to public addresses, never to private ranges, cluster addresses, or metadata endpoints.
Pod
Runs as uid 10001 with a read-only root filesystem, every capability dropped, no privilege escalation, seccomp RuntimeDefault, and no ServiceAccount token. The memory limit is the function's memory, and the CPU is proportional to it. Only /tmp is writable (512 Mi).
Optional gVisor sandbox
After hack/k8s/gvisor-up.sh and with K8S_RUNTIME_CLASS=gvisor, the pod's system calls go to a user-space kernel instead of the node's. It adds 2–5 s to a cold start.

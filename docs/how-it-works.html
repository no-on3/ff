Overview

You send code to the backend, inline or as a package with its libraries. The backend makes inline code a package of one file, keeps the package's zip in S3, and makes the package an image, which it pushes to the code registry. It keeps the function's record in PostgreSQL, and a copy of inline code in S3, then asks Kubernetes for your tenant's namespace and guardrails, a Service, and a Deployment whose pods mount that image. Kubernetes starts a pod from the runtime image; the node pulls the code image and mounts it read-only at /var/task, and the runtime loads your code once and reports ready. On each invocation the backend forwards your input to the pod, the runtime calls handler(event, context) in a worker, and the result travels back and is recorded with its duration. Idle functions are scaled to zero and start again on the next call. Work that runs later waits in PostgreSQL, in one table of messages: a call that doesn't wait, a queue's messages that AWS's SDKs send, a file's event; the backend's own workers take it from there, as the simulator's three scenarios of background work show. Data model

These tables hold everything the backend knows: functions with their invocations and metrics, and what else a function has: its environment (its variables and secrets, sealed with a key of its own), its URL with the customer's own domains for it, and its schedules; the packages functions run, each a zip of its account's, named by its SHA-256; accounts, with their plans, users, memberships, invitations and API keys (P-12 to P-16); and tables written once and never changed, which a trigger guards: the audit log (P-17), the usage records (P-20) and the capacity samples (P-21). A function belongs to an account, and its invocations, metrics, environment, URL with its domains, and schedules are deleted with it (ON DELETE CASCADE). Its usage records and capacity samples have no foreign key, so they outlive it, and both tables have a partition per month. An account has each package once (account_id and code_sha256 are unique together); a function names the one its pods run in package_sha256, an uploaded package or the one the backend made of its inline code, without a foreign key: the hourly purge reads that column, and deletes a package that no function names an hour after its last use. The platform's settings, which operators change from the admin dashboard, are in platform_settings (P-70), and the prices in price_books, each valid from its start until the next one's, never changed once started (P-30). Money is in a double-entry ledger (P-31): ledger_transactions, each with its ledger_entries on ledger_accounts, a customer account's wallet or one of FF's own. An entry's amount is whole minor units (millimes for TND), signed, added to its account's balance; a transaction's entries sum to zero in each currency, which the database checks when it commits, and nothing in the ledger is ever changed or deleted. Usage reaches it through the hourly rating (P-32): each settled hour's usage is summed into usage_hourly, each account's charge for the hour goes to usage_charges, debited or, in shadow mode, only recorded, and rating_runs lists the hours rated. The balance check reads the wallet before each invoke (P-33), and low_balance_notices keeps the low-balance e-mails sent, once per share of the last credit. Credit comes by bank transfer (P-35): payments holds each pro-forma an owner asked for, and the transfer and withholding certificate an operator recorded against it, each credit a ledger transaction. Each month's credit is invoiced (P-36): invoices and invoice_lines, written once when an operator issues them, numbered from invoice_counters without gap in each fiscal year, at the rates of tax_rates, which are dated data; invoice_notices keeps the operator's e-mails about them. A user belongs to accounts through memberships, each with a role. The schema comes only from migrations (BE/src/migrations), in every environment: npm run migration:run applies them as a separate step, and the backend refuses to start while one is pending. Columns are snake_case in the database, while the API's JSON keeps camelCase (account_id is accountId).

Not shown: the status values DELETED of functions and SUCCESS of function_invocations, which exist in the enums but are never set.

Inside the runtime

Every function pod runs one of two images, ff-runtime-nodejs:24-v3 or ff-runtime-python:3.13-v3, which speak the same protocol (version 2). Your code never runs in the main process: Node.js uses a worker thread with V8 heap limits, and Python a separate worker process with a memory budget. The main process therefore keeps answering probes, enforces the timeout, and replaces the worker after a timeout, an out-of-memory error, or a crash, without restarting the container. If that replacement can't load code that loaded before, the environment is broken, so the runtime exits and Kubernetes restarts the container. Your code runs in /var/task, as on Lambda.

What the runtime answers

HTTPerrorTypeWhen

Errors from an invocation carry x-ff-function-error: Unhandled. The backend records Sandbox.Timedout as an invocation with status TIMEOUT and every other error as ERROR, then answers the caller with 400 and "<errorType>: <message>"; a full queue answers 429 with TooManyRequestsException. A platform failure, such as an unreachable pod, answers 500 with a generic message and the request ID, and the history records it the same way; the details go only to the server log (D4 of the client-readiness plan). A call that gets no answer within the backend's own wait (see the limits below) is TIMEOUT too, with No response within … ms, in both invoke modes. The duration and memory the runtime measured are kept for failed calls too, and every outcome gets its usage record: errors are billed their duration and timeouts the function's timeout, while a full queue and platform failures aren't billed (D7).

Isolation and limits

Each layer narrows what a tenant's code, or a compromised backend, can reach.

Kubernetes API: RBAC and an admission policy
The backend's ServiceAccount ff-system/ff-controller may manage only the objects functions need: no exec into pods, no changes to RBAC. Secrets it may create, patch, update and delete, and never get, list or watch: a function's variables and secrets go into a Secret in its account's namespace, fn-<id>-env-0 or -env-1 in turn, which its pods read through envFrom, so that no value is ever in a pod's spec, which the backend can read. The admission policy ff-controller-scope confines its writes, and its calls through a Service's proxy, to namespaces named ff-t-* and labelled app.kubernetes.io/managed-by=ff-controller. Only the development setup grants that proxy: in production the backend runs inside the cluster and calls the Services directly. Reads are cluster-wide, Secrets excepted, which the beta accepts under rules listed in deploy/k8s/README.md.
Tenant namespace ff-t-…
Pod Security restricted. A ResourceQuota sized by the account's plan (beta: 20 pods, 8 CPU, 8 Gi), with 60 ConfigMaps and 30 Services, a LimitRange, and the NetworkPolicy ff-default-deny: ingress only from the backend's pods in ff-system; egress only to DNS, and to public addresses once you turn the account's internet egress on in the admin dashboard, never to private ranges, cluster addresses, or metadata endpoints. Every deploy, plan change and egress change writes the quota and the policy again, under a lock on the account, so a deploy under way can't put an old value back.
Pod
Runs as uid 10001 with a read-only root filesystem, every capability dropped, no privilege escalation, seccomp RuntimeDefault, and no ServiceAccount token. The memory limit is the function's memory, and the CPU is proportional to it. Only /tmp is writable (512 Mi).
gVisor sandbox: optional in development, required in production
After hack/k8s/gvisor-up.sh and with K8S_RUNTIME_CLASS=gvisor, the pod's system calls go to a user-space kernel instead of the node's. In production the backend refuses to start without it. A 128 MB Node.js function is ready 6 to 11 s after its deploy in it, against 6 to 8 s without (hack/k8s/cold-start-benchmark.sh).
Runtime worker
One invocation at a time, a hard timeout, a memory budget, and a fresh worker after any timeout, out-of-memory error, or crash.

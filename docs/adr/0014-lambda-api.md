## Context

FF speaks four of AWS's APIs already, each a port of the backend's own behind the edge: S3 (3002), SQS (3003), the sites (3004) and SES (3005), where the checks of keys, plans and credit live. Its functions are made and called through FF's own API, the console and `ff`. "No lock-in" means more: `aws lambda …`, AWS's SDKs, Terraform's AWS provider and the SAM CLI working against FF with one endpoint setting, as they work against AWS.

Three things stood in the way. Each front door reads Signature Version 4 with a copy of its own, and Lambda's paths are signed as SES's, not as S3's. FF's API keys keep only a hash of their secret, so they can't check a signature: the account's access keys (`AKFF…`, made for buckets) reach no function. And a function's own key works until the function is deleted, where a Lambda role's credentials end within 12 hours (decision 10's promise).

### What AWS's tools call, measured

`hack/spikes/lambda/`: a minimal Lambda endpoint, Node.js's standard library alone, D2's 41 operations in memory, a function `Pending` for 3 s and an update `InProgress` for 2 s as Lambda's are, every request recorded whole as signed. Against it, the AWS CLI 2.34.32, the SDK for JavaScript 3.1156.0 and boto3 1.43.118 each took a function through its whole life (made, waited for, called with its log's tail and without waiting, 6 MB of code, its settings, a version, an alias called by name and by ARN, a URL, a permission, an SQS mapping, async settings, a concurrency, tags, every read, deleted); Terraform's AWS provider 6.69.1, with OpenTofu 1.13.1 and Terraform 1.16.6, applied, planned again and destroyed what the reference modules hold; the SAM CLI 1.169.0 validated and built a small app.

| What | Measured |
|---|---|
| Operations | D2's alone, from every tool; 168 requests from the three clients, 49 from the provider, none from the SAM CLI, which checks and builds offline |
| Paths | signed as every service but S3 signs them, each segment escaped again: an ARN in a path, `arn%3Aaws%3Alambda…` on the wire, is signed over `arn%253Aaws%253Alambda…` |
| Signed headers | the SDK for JavaScript signs six headers, eight with a body, `x-amz-content-sha256` among them; boto3 and the CLI sign `host` and `x-amz-date`, with `content-type` for a body, and send no payload hash |
| Waits | `GetFunction` until `Active` or `Successful`: boto3 every 1 s for up to 5 minutes, the SDK from 1 s with jitter, the provider every 5 s, so a function made by Terraform costs at least 5 s |
| Refusals | `409 ResourceConflictException` (a call while `Pending`, a change during a change) and `400 UnknownOperationException` (an operation FF doesn't offer yet) shown at once, never retried; `404 ResourceNotFoundException` the clients' own modeled exception |

| A clean plan | an alias with no second version answers without `RoutingConfig`, and async settings answer only what was set: Lambda's defaults sent back read to the provider as a change to make each time |

### A key's end and a pod's replacement, measured

`hack/spikes/keys/`: past its key's end, both SDKs show the service's own refusal at once, one request each (`ExpiredToken` for S3 and SQS, `ExpiredTokenException` for SES and Lambda). With `AWS_CREDENTIAL_EXPIRATION` in the environment, boto3 sends nothing and raises `RuntimeError: Credentials were refreshed, but the refreshed credentials are still expired.`, from 10 minutes before the key's end. A function at one instance, called without pause by four callers while its environment changed (a new Secret, then the rollout, the path a renewed key takes): none of 573 and 587 calls lost through FF's API and the cluster API's proxy, but 166 of 742 on production's path, straight to the function's Service, where the backend's kept-alive connections went on reaching the old pod, which answers `503 Runtime is shutting down` while it drains. With the fix below, the same run lost none of 569, 578 and 576. A rollout of one instance costs the cluster's API about 85 requests.

## Decision

### 1. A front door of the backend's own, on its own port

A sixth server of the backend's, on `FF_LAMBDA_PORT` (3006), at `https://lambda.<domain>` behind the edge, and inside the cluster at `ff-storage`'s fixed address, where functions reach it with their key and `AWS_ENDPOINT_URL_LAMBDA`. Lambda's REST API in JSON, at the dated paths AWS documents for each operation; a function named by its name, its ARN or its partial ARN, with `:version` or `:alias` after it. Each answer carries `x-amzn-RequestId`; each refusal comes in Lambda's error shape, its type in `x-amzn-ErrorType`; another account's function answers as a missing one. It is a translation over FF's own services, as the SQS endpoint is: nothing about a function differs by the way it came, and the audit log names the access key.

### 2. 41 operations first, the others refused saying they come later

The plan's D2: functions, `Invoke`, versions and aliases, URLs, SQS mappings, async settings, permissions, concurrency, tags, `GetAccountSettings`, which the spike found the tools call and no other. Every other operation answers `400 UnknownOperationException`, naming it and saying FF doesn't offer it yet, which every client shows at once and none retries. The two operations that carry code take a body of up to about 67 MB, Lambda's 50 MB zipped in base64.

### 3. One signature check for every AWS API

One module reads and checks Signature Version 4 for every front door, told three things by each: its service's name, how its paths are signed (S3's way, or each segment escaped twice, as the spike measured for Lambda), and its error words. It checks the headers each client names, whatever they are, and takes the payload's hash from `x-amz-content-sha256` when there is one and from the body when there isn't. It is tested against AWS's published Signature Version 4 suite and the spike's recordings, and the three readers of today move onto it, their tests passing as they are. An `AWS_IAM` function URL also takes a request signed for `lambda` by a key that may invoke the function.

### 4. Access keys that reach functions, at three levels

The account's access keys may name the functions they reach, or all of them, at one of three levels close to how IAM groups Lambda's actions: **read**, **invoke** (and so an `AWS_IAM` URL), **write**. A key made before this step reaches no function until it is given some. Keys get names, and an account may have more than two. A function's own key may invoke its account's functions, as a role allowed `lambda:InvokeFunction`.

### 5. A function's own key lasts 12 hours, and no call is lost when it is renewed

A function's own key works 12 hours, as a role's session can last. At half its life the backend writes a new one into the function's environment Secret and replaces its pods one at a time, each new pod ready before an old one goes; a function scaled to zero starts with a fresh key. The variables stay those of today, with `AWS_ENDPOINT_URL_LAMBDA` beside them: no session token, and no `AWS_CREDENTIAL_EXPIRATION`, with which boto3 fails before the key does and says nothing of why. An expired key is refused in each service's words, as the SDKs show them.

**First, a rollout loses no call** (X-08's part 1, done before the rest). Told to stop, a runtime answers the call it runs and refuses every other, one waiting its turn or one that comes on a connection still open, with `503` and `X-FF-Not-Run: shutting-down`: the call never ran. Each answer closes its connection, so that the caller's next call opens one the Service gives a ready pod. The runtime closes no other connection itself, since a call could be crossing it and would be lost: it waits for its callers to close them, the backend each one it leaves unused for 5 seconds, and exits once nothing runs and no connection is open, at the latest a second past the function's timeout or those 5 seconds. The backend tries a call refused as never run again, on a connection of its own, as it tries a connection refused, for 5 seconds from the first refusal. And a pod leaves its Service 5 seconds before its runtime is told to stop (a `preStop` sleep), answering as before what still reaches it while each node's rules follow, so that no new connection finds a runtime that has stopped listening; the old key is revoked once no pod runs with it, those told to stop among them. Every rollout of a busy function gains it, a deploy's and a scale-down's as much as a renewal's. The renewal's cost is small: a hundred warm functions make 17 rollouts an hour, 17 Secrets written and about 1,400 requests to the cluster's API, and a renewal needs only the Secret and the Deployment of a deploy's seven applies.

### 6. Changes answered at once, as Lambda answers them

`CreateFunction` answers at once with `State: Pending`, an update with `LastUpdateStatus: InProgress`; FF's rollout goes on after the answer, a real instance checked and a failure rolled back, and `GetFunction` then says `Active` or `Successful`, or `Failed` with its reason, the previous version still live. A second change while one rolls out is refused with `ResourceConflictException`, which the clients wait out with their waiters rather than retry; `RevisionId` is checked as Lambda checks it. `GetFunction` must be cheap: the waiters ask it every second.

### 7. Each of Lambda's settings kept, mapped onto FF's, or refused aloud

The plan's D7: the role, the description, tags and the log's settings kept as given; the runtime, the code (a zip in the request or in a bucket the key reaches), the reserved concurrency, the dead-letter queue, the variables, the architecture and `/tmp` mapped onto FF's; what would change what runs and FF can't do (a VPC, layers, a KMS key, file systems, images, SnapStart, code signing, active tracing, object versions) refused, saying why. Permissions are kept as sent and given back, not enforced: FF's keys and URLs decide, and that is said everywhere.

### 8. Invoke, as Lambda's

A function that threw or timed out answers 200 with `X-Amz-Function-Error: Unhandled` and Lambda's error document; `X-Amz-Executed-Version` names the version that ran; `X-Amz-Log-Type: Tail` gets the call's last 4 KB of output in `X-Amz-Log-Result`, which the runtimes give back with their answer, since the log store sees lines about 5 seconds late. `Event` 202 and `DryRun` 204; `413 RequestTooLargeException` and `429 TooManyRequestsException`, with its reason, as Lambda's.

## As built: what comes later (X-09, part 3, 2026-11-03)

- **Lambda's other 47 operations are named in their refusal** (`LATER_OPERATIONS`, `BE/src/lambda/lambda-operations.ts`), each found by its method, its dated path and, for the two pairs that share a path, its query, as Lambda's model tells them apart: `GetLayerVersionByArn` by `find=LayerVersion`, `ListProvisionedConcurrencyConfigs` by `List=ALL`. Each answers `400 UnknownOperationException`, "FF doesn't offer ListLayers of Lambda's API yet.", the words of the 41's operations not built yet, and one sentence more where FF has another way: a function's zip carries its libraries, for layers; a function's `minInstances`, for provisioned concurrency; `Invoke` with `InvocationType` `Event`, for `InvokeAsync`, which AWS deprecated for it. A request that is none of Lambda's operations still answers with its method and its path, and every refusal still comes once the key is known to be good.
- **Lambda's model is the list's measure:** botocore 1.43.118's 88 operations, each one's name, method and URI, are kept beside the specs (`BE/src/lambda/lambda-api-model/operations.json`). L1 checks that the 41 and the 47 are those 88, each once; that each is found by its method, its path with every label given a value as a client escapes it, and its query; and that the guide's section names each one. The file taken again from a newer botocore fails the first check for each operation AWS added, until it is in one list or the other.
- **A layer's zip is read to Lambda's limit for it,** the code's 50 MB in base64, so that `PublishLayerVersion` is refused by its name and not as too large; any other of the 47 to the 6 MB of any operation.
- **None is tried again, measured:** the AWS CLI 2.34.32 sends each once, its debug log counted (L4's `lambda_reads`); the SDK for JavaScript, with its default three attempts, makes one (`$metadata.attempts`); boto3, with its default retries, makes none more (`RetryAttempts`), each naming the operation it called (`lambda_sdks`), as the spike had found for `ListLayers`.
- **D2's "later" list also names event sources other than SQS and event filtering:** they are fields of `CreateEventSourceMapping`, not operations, which X-10's part 2 refuses as it builds the mappings.
- **The guide's section,** "Functions through Lambda's API" in getting-started, says how to reach the endpoint and lists the 41, those answering now and those taken until they are built, and the 47 by group.
- **Refactored on the way:** one refusal for an operation not offered, `notOffered`, where the front door wrote the message twice; a body's refusal names the operation whichever list has it.
- **Tested:** L1 176 suites and 2,640 tests (175 and 2,633 before); L4's `--only lambda_sdks` **60 checks** (56 before): the CLI's three refusals and the sentence after one, and a check more for each SDK.

## Consequences

- AWS's tools reach FF's functions with one endpoint setting, signed as they sign for AWS, and what FF doesn't do yet is said in Lambda's own words, not retried.
- One signature check instead of three: what matters most is in one place, tested once, against AWS's suite and the recordings.
- Keys gain names, levels and functions; a key of before reaches nothing new, so no key gains a right it didn't have.
- A key copied out of a function stops working within 12 hours. The fix that makes its renewal lose no call came first, and makes every deploy and scale-down of a busy function lose none too, where production lost some before it.
- A pod told to stop lives 5 seconds longer out of its Service, then up to 5 more while the backend's connections to it close, and in development, where the cluster API's proxy keeps its own 90 seconds, until the runtime's limit: a second past the function's timeout or those 5 seconds.
- The nightly's `tools` job tries each tool's newest release against the recordings: a change in what a tool sends is known the next morning.
- What is not here: Lambda's other operations, IAM's policies, and the Lambda service as a server of its own, which the same code can become later, as the website server could.

## Alternatives considered

- **A Lambda server apart from the backend:** a seventh deployment, its own copy of the checks of keys, plans and credit, for an API that is a translation of the backend's own. The front doors' pattern keeps one place for them; a server of its own can come from the same code.
- **Lambda's whole API at once:** about 70 operations, where the tools call 41; the others are refused saying they come later, which no client retries.
- **Temporary credentials with a session token, as STS gives:** every front door would have to learn tokens, for no more protection than an expiry gives a key that the backend renews.
- **`AWS_CREDENTIAL_EXPIRATION` beside the key, so that SDKs know its end:** boto3 then fails 10 minutes before the key does, with a message that names nothing.
- **Renewing keys by restarting pods all at once:** every call in flight lost, and every caller's next one refused while the pods start.
- **Trying again a call whose kept-alive connection was reset:** what Node.js's documentation suggests for a request that can be sent twice, but a call's connection is reset too when its pod dies under it, and the call would run again. HTTP says a client should not send again on its own a request that may have been applied, a POST's, unless it knows it was not; the runtimes say which calls never ran, and close no connection a call could be crossing.
- **Holding each pod a few seconds before it stops** (a `preStop` sleep) **alone,** the usual remedy: the Service's endpoints move first, but connections kept alive still lead to the old pod, which the runtimes' refusals then send to another. FF has both since GitHub's run of 2026-11-02 (below): the delay for the new connections that the nodes' rules still lead to a pod stopping, the refusals for those kept alive.

## As built: one signature check (X-07, part 1, 2026-11-02)

- **One module,** `BE/src/common/signature-v4.ts`. Each front door tells it its service's name, how it signs a path, and its words for each problem a signature can have: a session token, another algorithm, a part missing, a malformed credential, another service, no time or a malformed one, a time on another day than the credential's or more than 15 minutes away, the host unsigned, another signature. S3's reader (`BE/src/storage/s3-signature.ts`, renamed from `sigv4.ts`) keeps its presigned URLs and `x-amz-content-sha256` on top, and `aws-chunked.ts` its streaming chunks, chained from what the check answers. SQS's and SES's readers are a few lines each, with the same words; Lambda's will use them too.
- **The paths:** S3's, each segment encoded once and nothing normalized, then the path as sent, which some clients sign. Every other service's: the path as sent, normalized (no empty or `.` segment, each `..` taking the one before) and escaped once more, as AWS's signers make it, so that `%3A` on the wire is `%253A`; then each segment escaped twice as the client meant it, for a client that sent it unescaped, as SES's reader did before.
- **The body's hash, for every service but S3, is the body's own,** never taken from `x-amz-content-sha256` on its word: the SDK for JavaScript sends the body's hash there in each of the 57 Lambda requests the spike recorded with their body, and boto3, the CLI and Terraform don't send it, so the same requests pass.
- **Tested against AWS's published suite,** `aws-c-auth`'s, its 38 cases at commit `3d29adc` in `BE/src/common/signature-v4-suite/` (Apache 2.0, its notice beside it): each case's canonical request, string to sign and signature, signed in a header and presigned in a query, the path in S3's form or every other service's as the case says; each header-signed request read and checked whole, passed with the key's secret and refused with another or another method; the three cases with a session token refused, as FF never issues one. A call signed for `lambda` by AWS's own signer, its path an ARN, passes, and is refused signed with its path escaped once. The S3, SQS and SES readers' tests pass as they were, but for the module they import from. The spike's recordings are replayed with Lambda's front door (X-09).

## As built: keys that reach functions (X-07, part 2, 2026-11-02)

- **Three columns on `storage_keys`** (migration `AccessKeyFunctions`): `name`, as an IAM user's (1 to 64 of `[A-Za-z0-9+=,.@_-]`), unique among the account's working keys by a partial index, a key made before named its ID, a function's or a deploy's key none; `functions`, the names or `*`; `function_access`, `read`, `invoke` or `write`. Two checks keep the level a known one and present exactly when functions are. The functions named need not exist yet, as a key's buckets need not.
- **What a key reaches** (`BE/src/storage/key-reach.ts`): naming nothing, every bucket and queue and the mail, and no function, as every key made before; naming buckets, queues or functions, those alone. So a key that names functions alone reaches no bucket, queue or mail, and a key of before gains no function. Its `readOnly` is its buckets', queues' and mail's; its functions have their level.
- **No update:** a key stays as it was made, and another reach is another key, as revoking and making one replaces an IAM user's key.
- **The plan's `accessKeys`,** 10 on beta, where an account had two: an IAM user has two keys, and an account has many users. Counted under the account's lock; past it, 400 in the plans' words (`The Beta plan allows 10 access keys, and the account has 10: revoke one first`); a name taken, 409.
- **An API key** makes a key that reaches functions only with the scope of its level (`functions:read`, `functions:invoke`, `functions:write`) beside `storage:write`, so that a key to the account's storage can't give itself the right to deploy code.
- **Down** removes the plans' limit, revokes each key that named functions alone (it would reach everything without its column), and drops the columns.

## As built: signed function URLs (X-07, part 3, 2026-11-02)

- **What a key may do with a function** (`functionAccessOf` and `mayInvoke` in `BE/src/storage/key-reach.ts`, which the Lambda endpoint will use too): a function's own key, `invoke` with every function of its account, as a role allowed `lambda:InvokeFunction`, and nothing more; an account's key, its level with the functions it names, or with all for `*`; nothing with any other. `invoke` and `write` invoke; `read` doesn't.
- **An `AWS_IAM` URL** takes `Authorization: AWS4-HMAC-SHA256 …` signed for `lambda`, read and checked by the one module, its path as every service but S3 signs one, its body read first for its hash: AWS's SDKs' signers pass, and `curl --aws-sigv4 "aws:amz:<region>:lambda"`. In this order: the signature (a key FF doesn't know or revoked, `The security token included in the request is invalid.`, one past its end `… is expired.` since X-08's part 2; a session token invalid, as FF issues none), then the key's account (another account's key, rightly signed, gets `Forbidden` alone, as another account's API key does; checked after the signature, so that a key's ID says nothing of whose the URL is), then what it reaches (`the access key <name> (<ID>) doesn't reach this URL's function`, or `may read this URL's function, not invoke it`), then the account's state, as for every call. Each refusal is 403 and `{"Message": "Forbidden: …"}`, the URLs' own shape; Lambda's error shape is its endpoint's. The key's last use is written down, as at the other front doors; what it used is in the call's history, by its source `url`.
- **The event names the caller** in `requestContext.authorizer.iam`: `accessKey` the key's ID, `userId` and `callerId` the key's name (its ID for a key without one), a function's own key its function's ID; the `authorization` header is kept from the function, and from the history, as an API key's.
- **An FF API key still works there** (`Authorization: Bearer ffk_…`, with `functions:invoke`, made by an owner or a developer), as decision 16 said: what AWS doesn't take, which `ff doctor --deployed` and the export's notes say. A request with neither gets 403 saying both.
- **Signed in a header only:** a URL presigned in its query (`X-Amz-Signature`) isn't read, and is refused as a request without credentials: AWS's SDKs and CLI sign a call in its headers.

## As built: keys that end (X-08, part 2, 2026-11-02)

- **A key past its end is refused in its service's words,** where it was refused as one FF doesn't know: the key's lookup (`StorageDirectory.key()`) answers `expired` for a key whose `expires_at` has passed, and each front door says so. S3: `400 ExpiredToken`, `The provided token has expired.`; SQS: `403 ExpiredToken` in its query code, `ExpiredTokenException` in its JSON shape, `The security token included in the request is expired`; SES: `403 ExpiredTokenException`, the same words; a function's URL: `403 Forbidden: The security token included in the request is expired.` A deploy's key, an hour long, ends so too. A key revoked, or one FF doesn't know, is refused as before.
- **A function's key lasts 12 hours** (`FUNCTION_KEY_LIFE_MS`), its `expires_at` written as it is made. A key renewed is marked, not revoked: the column `replaced_at` (migration `FunctionKeyRenewal`), and the unique index of a function's working key counts the keys neither revoked nor replaced, so that the old key and the new work side by side while the pods are replaced. `FunctionKeys.credentialsFor()`, which every rollout calls, makes the function's key when it has none and renews it when it is past half its life: one transaction marks the old replaced and writes the new, and a second renewal at the same moment, in another backend, finds the old one marked and takes the new. A function's key made before has no end, and works on until it is revoked (part 3).
- **The renewal** (`FunctionKeyRenewal`, `BE/src/functions/key-renewal.service.ts`) runs every `FF_KEY_RENEWAL_INTERVAL_SECONDS` (60) in one backend at a time, under the jobs' lock. A turn reads, in one query, the functions whose key is past half its life or that have keys replaced, and the cluster's Deployments in one list. A function with no instance asked is left to its next start. Of the others, each Deployment, `$LATEST`'s and its versions', whose template names another environment revision is given the function's workload as it runs, the current key in its environment: its environment Secret written, then its Deployment, the template alone changed (`Orchestrator.renewEnvironment()`), so its pods are replaced one at a time, a new one ready before an old one goes; the turn waits until it's ready, then takes the next. A Deployment whose template differs by more than the key, its code or its variables, is left to the change that wrote it, under way or failed, which brings the current key with it: the function waits for a later turn. A turn that finds each of a function's Deployments on the current key revokes the keys it replaced, so that no pod holds a revoked key: for one rolled out, the next turn.
- **From zero,** a call to a function scaled to zero whose key is due brings its workload with a new key, which is written into its template before its pod starts (the call's `start`, at one instance); one whose key isn't due is scaled to one as before. A version's first call deploys it with the current key, as before.
- **Fixed with it:** waiting for a version's rollout would have deleted `$LATEST`'s environment Secrets, since the wait deletes the Secrets its Deployment doesn't read, and a version's reads one of its own; only `$LATEST`'s wait deletes them now. No version's wait reached that code before the renewal.
- **Tested:** L1 for each front door's refusal, the orchestrator's renewal in two writes and the cold start with a fresh key; L2 for the key's life (its end, due at half of it, two renewals at once, past its end said expired, a lasting key never renewed, every key revoked with its function) and for the job against a stand-in cluster (each Deployment rolled in turn and the old key revoked a turn later, an idle function left to its start, a Deployment an update is rolling out left to it, a cluster's failure counted while the others are renewed, a function that isn't `ACTIVE` left); L3 for a function at two instances called without pause by four callers through its renewal's rollout, none lost, and one at zero starting on a fresh key; L4 for a function's key copied out of its pod and aged past its end in SQL, the function at zero: refused at S3, SQS, SES and its URL, then a call starting the function on a fresh key, the old one revoked a turn later; and that key aged six hours, the function running and called each second, renewed by the job, every call answered. An account's key never ends: one given an end in SQL is no more the account's, and its revoke answers 404.

## As built: the keys of before (X-08, part 3, 2026-11-02)

- **A lasting key is due at once.** A function's key with no end, made before keys ended, is due as one past half its life is, so that the function's next workload replaces it, and the renewal lists it as lasting. Its first turn after the upgrade renews it for every function, one scaled to zero too: since a lasting key never ends on its own, the function's templates are written with the new key, and no pod starts. A function with no Deployment has it revoked at once (`FunctionKeys.revokeLasting()`): no pod holds it, and its next rollout makes it a key. The turn after revokes the keys replaced. So within two turns of the upgrade, two minutes, and longer only for rollouts that take longer, no function holds a key that lasts: a key copied out of a function stops working within 12 hours.
- **The cost,** as X-01's spike measured it (§5): a rollout of one instance makes about 85 requests to the cluster's API, so a hundred warm functions renewed every 6 hours make 17 rollouts, 17 Secrets written and about 1,400 requests an hour. The upgrade's first turn rolls every running function once, one after another, holding the job's lock until the last is done: for a hundred, about 8,500 requests over a quarter of an hour, at the spike's 7.4 s a rollout. A turn with nothing due asks the cluster nothing: its one query finds nothing, and it lists no Deployment.
- **The platform's suite carries a function across a renewal,** on the platform as deployed, in gVisor: the function that writes to its bucket with its own key, its key aged six hours in SQL, the renewal's pace 5 s in the suite's overlay, called each second until the old key is revoked, every call answered, then with the new key.
- **Tested:** L2's keys (a lasting key due at once, listed, replaced by one that ends; revoked alone when asked) and job (a lasting key renewed at zero, no pod started, revoked the turn after; that of a function with no Deployment revoked at once, its next rollout making one that ends); L4's `key_life` (a key from before, the function at zero, replaced and revoked, its next call on the new key); the platform's suite on GitHub.

## As built: Invoke (X-10, part 1, 2026-11-03)

- **`Invoke` answers as Lambda's** (`BE/src/lambda/lambda-invoke.ts`), over the call FF's API and the URLs make (`FunctionsService.call`). `RequestResponse` answers 200 with the function's answer as its runtime sent it, byte for byte. - **The call's log, from the runtimes:** asked with `x-ff-log-type: Tail`, both runtimes give back the call's last 4 KB of log, `START` to `REPORT`, both streams merged line by line, as `x-ff-log-result` (protocol 3, two optional headers, `8cda4ca`). The backend passes it on as `X-Amz-Log-Result`, a failed call's too.

- **Refused as Lambda refuses:**
  - A payload past 6 MB, or an `Event`'s past 1 MB: `413 RequestEntityTooLargeException`, "Request must be smaller than 6291456 bytes for the InvokeFunction operation".

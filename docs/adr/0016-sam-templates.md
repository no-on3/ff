## Context

On AWS, an app's functions, URLs, queues, buckets and events are often one file: a SAM template, `template.yaml`, which `sam build` builds and `sam deploy` turns into a CloudFormation stack. On FF, nothing reads one: `ff deploy` takes a folder or a file with flags, and the small app is set up by about twenty `ff` commands. A template that `sam deploy` takes as it is on AWS, and `ff deploy` on FF, is the parent plan's ADR-009, and the export kit (X-02) writes one back.

### What the SAM CLI does with a template, measured

`hack/spikes/lambda/`'s SAM part: the SAM CLI 1.169.0 on a small app's template (a function with a public URL, an SQS event and an alias published with each change, its queue, a bucket), every AWS endpoint pointed at the spike's. `sam validate`, `sam validate --lint` and `sam build` asked AWS nothing. `--lint` refuses a region outside AWS's list, FF's among them (`Regions ['tn-tunis-1'] are unsupported`, cfn-lint's words): the region only picks the resources' specification to check against, so a lint runs with one of AWS's and passes. `sam build` leaves `.aws-sam/build/`: a folder for each function, its code and its `node_modules`, and a template whose `CodeUri` names that folder.

### A template's YAML, read in Rust, measured

`hack/spikes/sam-yaml/`: a reader of about 300 lines on yaml-rust2 0.13's events, a crate of its own. Five templates read value for value as cfn-flip 1.3.0, AWS's own converter, reads them: `sam init`'s hello-world for Node.js and for Python, the small app, a fixture with all 18 of CloudFormation's short tags, and one of plain scalars. CloudFormation's guide says it supports YAML 1.1 with a few exceptions (no aliases, no merges, none of the `binary`, `omap`, `pairs`, `set` and `timestamp` tags), and cfn-flip and the SAM CLI read through PyYAML, YAML 1.1 too: typed as YAML 1.2, 12 of the fixture's 17 plain scalars read otherwise (`yes` a string, not a boolean; `0755` 755, not 493; `1:30` a string, not 90). yaml-rust2's events carry each value's line and column but not a tag's own position; serde_json keeps a template's order only with its `preserve_order` feature.

## Decision

### 1. `ff` reads the template, and FF's API does the rest

`ff deploy` in a folder with a `template.yaml` (or `--template`, or `sam build`'s `.aws-sam/build/template.yaml`) reads the template on the machine it runs on, as `sam deploy` does, builds each function's code as `ff package` builds it, and makes or changes what the template declares, in order, through FF's API. The backend never reads YAML: a template is the customer's file, and what reaches FF is the API's requests, checked as any are.

### 2. The template read as CloudFormation reads it

The reader is the spike's grown up (`cli/src/sam.rs`, brought into `ff` by X-04's `ff doctor`; X-12 builds on it), on yaml-rust2's events: each short tag in its long form, plain scalars typed by YAML 1.1's rules as CloudFormation and AWS's tools type them, and every value's line kept, so that each message names the file and the line. What CloudFormation doesn't take is refused at its line, before anything is made: an alias, a merge, YAML's tags it lists, a tag it doesn't have, a key given twice, a second document. A template FF takes is one AWS takes too.

### 3. The subset, and one refusal for what is outside it

The plan's D11: `Globals`; `Parameters` with `--parameter-overrides` and `samconfig.toml`; `!Ref`, `!GetAtt`, `!Sub`, `!Join` and the pseudo parameters as FF's (`AWS::Region`, `AWS::AccountId`, `AWS::StackName`); `AWS::Serverless::Function` with its code, handler, runtime, memory, timeout, description, environment, tags, reserved concurrency, URL, `AutoPublishAlias`, async settings and dead-letter queue, and its events of the types `Schedule`, `ScheduleV2`, `SQS`, `S3` and `HttpApi`; `AWS::SQS::Queue`; `AWS::S3::Bucket` with its notifications and its website; `AWS::Lambda::Permission`; `Outputs`, printed. `Policies` are read and left for AWS: on FF a function's key reaches its account. Anything else fails before any change, in one message listing every resource and key outside the subset, each with its line. Settled with `ff`'s reading of templates, since `ff export`'s own hold more: a function's `FunctionName` and `ProvisionedConcurrencyConfig` (FF's name and its warm instances), `Tracing` and `PackageType` at the one value FF has (`PassThrough` or `Disabled`, `Zip`), `Architectures` of `x86_64`, and its IAM settings (`Role`, `PermissionsBoundary`, `RolePath`, `AssumeRolePolicyDocument`) read and left for AWS as `Policies` are; `AWS::SQS::QueuePolicy` and `AWS::S3::BucketPolicy`, kept without effect as `AWS::Lambda::Permission` is; the pseudo parameter `AWS::Partition` too, `aws`, which FF's ARNs are in; the names SAM makes of a function, its URL (`<function>Url`), its alias (`<function>.Alias`) and its versions, and its role (`<function>Role`) refused, FF having no IAM. What CloudFormation or SAM would refuse too is told apart from what FF's subset hasn't: a name that names nothing, a function without its code, handler or runtime, a parameter's value outside what it allows.

### 4. A stack, kept by FF

A deploy's **stack**, named by `--stack-name` or `samconfig.toml`, is kept in FF (`/stacks`): for each resource the template made, its logical ID, its type and the FF resource it is; the parameters it was deployed with; and the template's SHA-256, to tell when it changed. Not the template's text: the template is the customer's, in their repository, as the code is. The next deploy changes the stack's resources, and removes those the template no longer has after asking (§9, 9); `ff delete-stack` removes them all, as `sam delete`. The console and `ff get` say when a function belongs to a stack.

**As built (X-12, part 2):** `GET /stacks`, `GET`, `PUT` and `DELETE /stacks/{name}`, under the scopes `stacks:read` and `stacks:write`. A `PUT` gives the stack whole, as a deploy left it. A resource's physical ID is the FF resource's name, a function's, a queue's or a bucket's, a version's number or an alias's name after a colon for what is a version's or an alias's, and null for what FF keeps without effect. A stack names only its account's functions, queues and buckets, each in one stack at most, so that two stacks never delete each other's. A `NoEcho` parameter's value is left out, FF keeping no copy of it. `DELETE` forgets the stack and leaves what it made, which `ff delete-stack` deletes first. An account has 2,000 stacks at most, CloudFormation's quota. A function's answers in FF's API name its stack, `stack`, null for none. FF's API takes three of Lambda's settings that a template gives and only Lambda's own endpoint took: a function's `description`, its `deadLetterTargetArn`, a queue of the account, and its `tags`, put once a create or an update is live and replaced whole, which a function's own answer carries.

**As built (X-12, part 2, the deploy):** `ff deploy <template.yaml>` reads the template with part 1's reader, its parameters' values as `sam deploy` gives them (the stack's last value for one not given, then `--parameter-overrides`, else `samconfig.toml`, then its Default), and plans its functions in `cli/src/sam/plan.rs`, a module of no calls: each one's name, its `FunctionName`, else the stack's last, else CloudFormation's (the stack's name, the logical ID and 12 random letters and digits, within 64 characters); its settings with the Globals merged and every intrinsic resolved, the pseudo parameters FF's region and account, a function's `Ref` its name and its `Arn`, its alias's and its version's ARNs FF's; and what the stack keeps of it, by SAM's logical IDs: `<function>`, `<function>Url`, `<function>Alias<alias>`, `<function>EventInvokeConfig`, and each `AWS::Lambda::Permission`, kept without effect. What the stack's last deploy made and this one doesn't, by type and FF resource, is deleted after asking, a function's own resources going with it. Every problem is said before any change: what FF can't know before the deploy (a function's URL in a variable), a `ReservedConcurrentExecutions` of 0, which stops every call and which Lambda's own endpoint sets, a `ProvisionedConcurrencyConfig` without `AutoPublishAlias`, a destination without its ARN, a variable named like a secret of the function's, a function of that name outside the stack, which `ff deploy` doesn't take over. Queues, buckets and events are refused until part 3. A folder's code is built as `ff deploy <folder>` builds it, once for functions that share it, and a .zip is deployed as it is, its files read for the handler's check; `sam build`'s template names folders built already. A new stack is saved empty first, so that a refusal changes nothing, and again after each function made, so that a deploy stopped halfway leaves what it made in the stack; the last save is the template's. `ReservedConcurrentExecutions` is the most instances a function runs, `ProvisionedConcurrencyConfig` those kept running, FF's default of 3 most and none kept when the template gives neither. `ff delete-stack` deletes what the stack made, a resource gone already passed over, then forgets the stack; `ff get` and the console's function page name a function's stack; `ff init --template sam` writes the hello world of §5.

**As built (X-12, part 3):** `ff init --template sam` writes `sam init`'s hello world, the SAM CLI 1.169.0's, with FF's changes alone: `nodejs24.x` for Node.js's `nodejs22.x`, `FunctionUrlConfig` for its `Api` event, its output `HelloWorldApi` the function's URL, its output of the IAM role SAM makes left out, and `events/event.json` a function URL's request, Lambda's payload of version 2.0; its handler is `sam init`'s, its test needs no library and sits outside the code's folder. A test compares it with `sam init`'s templates, kept as fixtures, and `sam validate --lint` takes it. [SAM templates on FF](../sam-templates.md) lists the subset for people.

**As built (X-13, part 1):** a function's events are planned with it. A `Schedule` event, an EventBridge rule, and a `ScheduleV2` event, EventBridge Scheduler's schedule, are each one of the function's schedules, named by its `Name`, else the event's key; its `Input` is JSON text, as EventBridge takes it, `State` or `Enabled` its state, and `at()`, a run once, is refused. An `SQS` event is the function reading the queue its ARN names, which has to be a queue of the account in FF's region, with Lambda's defaults where it says nothing, a batch of over 10 messages needing its window, as Lambda's. An `HttpApi` event gives its function a URL anyone may call, if its `FunctionUrlConfig` gives none: the subset takes one function's alone. With `AutoPublishAlias`, schedules and readers run the alias, as SAM's events do. The stack keeps each as `<function><event>`, of the type SAM makes (`AWS::Events::Rule`, `AWS::Scheduler::Schedule`, `AWS::Lambda::EventSourceMapping`), its physical ID the function's name and, after a colon, the schedule's or the queue's, which FF's API checks as the account's function's; a rule and a schedule of one name are the same schedule on FF, so an event that changes from one type to the other keeps it. Before any change, each expression is read by the API's own parser and each queue looked for. A schedule or a mapping of the function's made outside the template stays. `S3` events wait for part 2's buckets, as SAM writes them in their bucket's notifications.

**As built (X-13, part 2, the deletion policies):** each resource of a stack keeps its `DeletionPolicy`, `Delete` or `Retain` (`deletionPolicy` in FF's API, `Delete` when not given), a function's resources the function's, as SAM's transform passes it on. What the template no longer has, and what `ff delete-stack` meets, is deleted or, for `Retain`, left in the account and dropped from the stack, by the policy of the deploy that made it, as CloudFormation takes the previous template's for a resource removed. What a new name replaces under the same logical ID follows the new template's `UpdateReplacePolicy` instead. The deploy asks only about what it deletes, and says what it keeps (`kept` in `--output json`). A function left is the account's: a template that names it again is refused, as one outside the stack is, which matches CloudFormation's refusal of a name that exists.

**As built (X-13, part 2, the queues):** an `AWS::SQS::Queue` is a standard queue of the account, made through FF's API: named by its `QueueName`, else the stack's last, else CloudFormation's way within SQS's 80 characters; its five attributes the template's, else SQS's defaults, since CloudFormation sets back an attribute a template removes; its `RedrivePolicy` another queue of the account in FF's region, by its ARN, the queue itself and a circle of them refused; its `Tags`, CloudFormation's list, the queue's tags, which FF's API takes since this part, gives in a queue's own answer and replaces whole. The queues are made before the functions, each dead-letter queue before the queues that use it, so that a function's `DeadLetterQueue`, a destination and an `SQS` event can name one by `!GetAtt`; a deploy after changes what differs alone, and the queues the template no longer has are deleted after the functions. `!Ref` of a queue and its `QueueUrl` are the URL under `GET /me`'s `sqsFunctionEndpoint` in a function's variables and under the public endpoint in `Outputs`. Before any change, a queue of the template's name that the account has outside the stack is refused, as a function's is, and each dead-letter queue and each queue read that the template doesn't make is looked for. `AWS::SQS::QueuePolicy` is kept in the stack without effect, as `AWS::Lambda::Permission` is. A stack's resources come back from FF's API by logical ID, not in the order they were made, so the queues are deleted in that order: FF's SQS lets a dead-letter queue go while a queue still names it.

**As built (X-13, part 2, the buckets):** an `AWS::S3::Bucket` is a bucket of the account, made through FF's API: named by its `BucketName`, else the stack's last, else CloudFormation's way in lower case within S3's 63 characters, a name S3's rule refuses, dots among them on FF, refused before any change; its `Tags` the bucket's, which FF's API takes since this part and `PATCH /buckets/{name}` replaces whole; its `WebsiteConfiguration`'s `IndexDocument` and `ErrorDocument` its site, put when they differ and removed when the template has none, the single-page app's setting kept, as a template can't say it; and its `NotificationConfiguration`'s `LambdaConfigurations` and `QueueConfigurations`, each a function or a queue of the account in FF's region by its ARN, with its event and its key's filter. CloudFormation takes one event a configuration where S3's API takes a list: configurations of one destination and one filter are one on FF, so that a template `ff export` wrote, its configurations split by event, gives back the bucket's own. A function's `S3` event is a notification of the bucket its `!Ref` names, calling its alias under `AutoPublishAlias`, as SAM writes it into the bucket's. Each configuration's ID is the template's, `<bucket>Lambda<n>` and `<bucket>Queue<n>` in its order and `<function><event>` for an event, since CloudFormation's configurations have none: a deploy after compares the whole configuration with the bucket's and puts it only when they differ. The template says a bucket's notifications and its site as it says a queue's attributes: what it doesn't have, the bucket hasn't, those of `ff buckets notify` among them. Two notifications that could take one event, which S3 refuses as ambiguous, and more than S3's 100, are refused before any change, as are a function or a queue named that the account hasn't and the template doesn't make, and a bucket of the template's name that the account has outside the stack. The buckets are made first, so that a name another account has, which only the create can say since a bucket's name is its own across FF, stops the deploy before anything else; their notifications are put once the functions are made, which FF's API wants there. `!Ref` gives the bucket's name, `Arn` its ARN, `DomainName` and `RegionalDomainName` its host under `GET /me`'s S3 endpoint, and `WebsiteURL` the site's address, which FF's API gives once the site is made, so `Outputs` alone have it. A bucket the template no longer has is deleted after the functions and before the queues, when it is empty: one with files stops the deploy, or `ff delete-stack`, saying how to empty it, as CloudFormation fails to delete it. `AWS::S3::BucketPolicy` is kept in the stack without effect: on FF the account reaches its buckets, and a site is public by its configuration.

**As built (X-13, part 3, the round trip):** the template `ff export` writes is deployed back on FF by another account, in the `ff` suite: the small app's three functions exported with their values, their buckets renamed through their parameters and their secrets given, then compared with the first account's through FF's API, each function's runtime, handler, memory, timeout, instances, code, variables and URL with its CORS, its alias, its queue's attributes and its mapping, its bucket's tags and notifications. What differs is what the export says differs on AWS: a secret is a variable; the alias naming `$LATEST` is published, the function's queue then read through it; an alias naming a version stays out. The round trip found that a variable holding a bucket's name kept FF's name where the template renames the bucket: a variable that holds the name of one of the account's buckets now takes the bucket's name parameter, in the template and in `terraform/`, and one that holds a queue's name the queue's name, with or without `--with-values`. In L1, the plan of the export's own fixture is checked against the account it was written from, and every SAM template the repository keeps passes `sam validate --lint`, cfn-lint inside it (`hack/test-sam-fixtures.sh`, in the unit stage, the SAM CLI cached by version on GitHub).

### 5. What a template means on FF

`!Ref` of a queue in a function's environment gives the URL functions reach inside the cluster, so that AWS's SDK for JavaScript, which sends to the URL's host, keeps working. FF's secrets stay out of templates: set with `ff secrets` or `ff db create --secret-for`, and a template variable with a secret's name is refused. `sam init`'s hello-world, whose `Api` event FF doesn't have, is refused with a message naming `FunctionUrlConfig` and `HttpApi`, and `ff init --template sam` writes FF's variant of it, its output naming a function URL. FF's tools and documents lint a template with `sam validate --lint --region` and one of AWS's regions.

## Consequences

- One file describes an app on both: `sam deploy` takes it on AWS, `ff deploy` on FF, and the export kit writes it back.
- The `ff` command gains a YAML reader and its dependency, yaml-rust2, which the spike chose: maintained, the most used, its newest release weeks old, where serde_yaml is deprecated, serde_yml at 0.0.x and saphyr's newest days old.
- A template's mistakes are named at their line before anything changes, in CloudFormation's terms.
- A stack is FF's record of what a template made, so a resource removed from the template can be removed from FF; the template stays the customer's.
- `ff`'s JSON keeps a template's order only if X-12 turns serde_json's `preserve_order` on, which would change the order of every map `ff` prints: it keeps the order beside the values instead, or turns it on knowingly.
- What is not here: CloudFormation itself (FF builds no stacks of CloudFormation's own, What to build next §11), `Conditions` for now, nested stacks, and resources outside the subset.

## Alternatives considered

- **The backend reading templates:** a YAML parser and a template's semantics in the server every account calls, where the CLI can read the file on the customer's machine and send the API's requests, checked as any are.
- **A CloudFormation-compatible engine on FF:** CloudFormation's whole model, its resources and its rollbacks, for an app's dozen resources that FF's API already makes.
- **A YAML 1.2 reader, as yaml-rust2's own loader reads:** `yes`, `0755` and `1:30` would mean on FF what they don't on AWS.
- **serde_yaml or serde_yml:** the first deprecated, the second young; saphyr, yaml-rust2's successor, can replace it later, its events being the same in kind.
- **Keeping the template's text in the stack:** the customer's file twice, one copy out of date at the first edit.

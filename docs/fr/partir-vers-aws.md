# Partir vers AWS, avec `ff export`

Les fonctions de FF sont celles d'AWS Lambda ([Fonctions, comme AWS Lambda](fonctions.md)), ses compartiments ceux de S3, ses files celles de SQS, son courrier celui de SES : un compte part vers AWS avec son code tel qu'il est. `ff export` écrit ce qu'il faut pour partir dans un nouveau dossier, à partir des ressources du compte, avec la lecture des fonctions (`functions:read`) et celle des autres services, et celle de l'usage (`usage:read`) pour son estimation :

```bash
ff export ./vers-aws                                          # toutes les fonctions, files et compartiments du compte
ff export ./vers-aws --functions orders-api,orders-receipts   # celles-ci, avec les files et les compartiments qu'elles appellent, lisent ou utilisent
ff export ./vers-aws --with-values                            # les valeurs des variables dans le modèle, plutôt qu'en paramètres
```

| Dans le dossier | Ce qu'il contient |
|---|---|
| `template.yaml` | Un modèle AWS SAM : chaque fonction avec son rôle, son adresse, ses planifications, les files qu'elle lit et ses réglages d'appel sans attente ; les files ; les compartiments et leurs notifications, le nom de chacun un paramètre, ceux de S3 étant à tout le monde. Une variable d'une fonction qui contient le nom d'un compartiment prend ce paramètre, et celle qui contient le nom d'une file le `QueueName` de la file, pour qu'un nom changé en route atteigne le code |
| `template-before-copy.yaml` | Le même sans les notifications des compartiments, pour le premier déploiement, afin que la copie de leurs fichiers n'appelle rien |
| `terraform/` | La même chose pour OpenTofu ou Terraform, avec le fournisseur AWS, et `terraform.tfvars.example`, ses valeurs à remplir : l'un ou le modèle, pas les deux |
| `code/` | Le zip de chaque fonction, tel que Lambda l'exécute ; le TypeScript en ligne, comme le JavaScript que FF a exécuté |
| `secrets.template.env` | Les valeurs que le modèle prend et que l'export n'écrit pas, une ligne chacune : les variables des fonctions, sauf avec `--with-values`, hors celles qui contiennent le nom d'un compartiment ou d'une file, et leurs secrets, que FF ne montre jamais |
| `data/` | Comment part chaque sorte de ressource du compte, une page chacune, en anglais, avec les noms du compte en tête : les fonctions (`lambda.md`, vos domaines devant l'adresse d'une fonction compris), les bases de données, les caches, le courrier, les files, les sites, et `s3-sync.sh` pour les fichiers des compartiments |
| `MIGRATION.md` | Le déroulé du départ, dans l'ordre qui marche : les données, puis les files, puis les fonctions, chacune servie par FF jusqu'à ce que ses appelants partent ; et ce que le modèle change en route ou vous laisse |
| `cost-estimate.md` | Les trois derniers mois du compte aux prix d'AWS, une estimation, en anglais : une colonne par mois à côté du total de FF, et ce que suppose chaque ligne de ce qu'AWS facture et FF non ; avec une clé qui ne lit pas l'usage, pourquoi il n'y en a pas. `ff usage --aws` la donne aussi, à jour, et la page Usage de la console, où une case retire chacune de ces lignes des totaux |

**Le rôle de chaque fonction** permet ce que ses clés ont utilisé sur FF, que FF note une fois par jour pour chaque compartiment, file et identité de courrier, opération par opération (`GetObject`, `SendMessage`, `SendEmail`) : les modèles de politique de SAM là où la fonction a fait ce pour quoi l'un est fait, chacun sur son compartiment ou sa file (`S3ReadPolicy` pour un compartiment qu'elle a lu, `SQSSendMessagePolicy` pour une file où elle a envoyé, qu'elle ne peut alors pas lire, `SQSPollerPolicy` pour une file qu'elle a lue), et des déclarations pour le reste, comme `ses:SendEmail` sur l'identité depuis laquelle elle envoie. Dans `terraform/`, la même chose, action par action. Un usage que FF n'a jamais vu, comme celui d'une tâche mensuelle qui n'a pas tourné depuis que FF note, AWS le refuse (`AccessDenied`) tant que les `Policies` de la fonction ne le permettent pas : `MIGRATION.md` dit les jours que couvrent les usages.

**Versions et alias :** l'export prend le code de chaque fonction tel qu'il est, celui de `$LATEST`. Son alias qui nomme `$LATEST`, le premier par son nom s'il en a plusieurs, devient l'`AutoPublishAlias` du modèle et l'`aws_lambda_alias` de Terraform, que chaque déploiement fait pointer vers une nouvelle version du code ; l'adresse de la fonction, ses planifications, les files qu'elle lit et ses réglages d'appel sans attente passent alors par lui, comme SAM les y attache. Une fonction gardée chaude sans un tel alias reçoit `live`, qui porte sa concurrence provisionnée. `MIGRATION.md` dit le reste, chaque fois avec la commande de l'AWS CLI qui le crée chez AWS : un autre alias qui nomme `$LATEST` ; un alias qui nomme une version, dont l'export n'a pas le code ; l'adresse propre d'un alias, avec ses domaines, dont la bascule déplace les appelants avec ceux de la fonction ; et une planification, une lecture de file, une notification de compartiment ou une destination qui nomme une version ou un alias que les fichiers ne publient pas, et que les fichiers font appeler la fonction, ou l'alias qu'ils publient. `ff doctor --deployed` signale l'adresse d'un alias qui prend les clés de FF, et ses domaines, comme il signale celle de la fonction.

**Vérifiez d'abord le code :** `ff doctor <dossier>` lit le code d'une fonction, sans les dossiers de ses bibliothèques ni ses fichiers `.env`, et nomme chaque ligne qui marche sur FF et pas sur AWS Lambda, sous la forme `fichier:ligne: niveau: message [vérification]` (en anglais). Une erreur bloque le départ : une clé d'API de FF dans le code (`ffk_…`), un secret à révoquer, et un dossier de plus de 250 Mo décompressé, la limite de Lambda. Un avertissement est à juger : une variable que pose le runtime de FF (`FUNCTION_NAME`, que Lambda appelle `AWS_LAMBDA_FUNCTION_NAME`) ou qui commence par `FF_` ; les hôtes de FF, le domaine de votre profil et le `.svc.cluster.local` du cluster ; `event.body` lu comme un objet, comme le donnait l'événement d'origine de FF ([ADR 0007](../adr/0007-function-events.md)) ; un fichier écrit hors de `/tmp`, seul endroit où Lambda laisse écrire ; un handler TypeScript sans son JavaScript, que `ff package --compile` produit. Un `template.yaml` à côté du code est lu comme CloudFormation le lit : ce que CloudFormation ne lit pas est une erreur à sa ligne, comme la mémoire ou le délai d'une fonction au-delà de ceux de Lambda (128 à 10 240 Mo, 900 s) ; un runtime que Lambda a déprécié, Node.js 20 ou Python 3.10 et plus anciens en novembre 2026, est un avertissement, et une erreur dès que Lambda n'y crée plus de fonction ; un handler TypeScript y est un avertissement aussi, sauf si son `Metadata: BuildMethod: esbuild` le fait compiler par `sam build`. Ce que `ff deploy` ne prendrait pas du modèle est nommé aussi, par la lecture qu'en fait `ff` : chaque élément hors du sous-ensemble de SAM qu'a FF est un avertissement, puisqu'AWS le prend (l'événement `Api` de `sam init`, les `Conditions`, les couches, les tables DynamoDB, les ressources d'IAM, un runtime que FF n'a pas), et un nom qui ne nomme rien une erreur, comme CloudFormation le refuserait ; la valeur d'un paramètre est celle que prendrait `sam deploy`, de `--parameter-overrides` ou sinon de `samconfig.toml`, et une valeur que CloudFormation refuserait est une erreur. Les fichiers `.tf` d'un projet Terraform sont lus pour le bloc de leur provider AWS : un bloc `endpoints` est une erreur, et chaque réglage dont FF a besoin (les quatre `skip_…`, `s3_use_path_style`) un avertissement, `.terraform/` laissé de côté. Il lit des lignes, pas le sens du code : une remarque est une ligne à regarder. Il sort avec 1 sur une erreur, et avec `--strict` sur un avertissement aussi, pour un job de CI ; `--output json` liste les remarques.

**Ce qui pointe encore vers FF :** `ff doctor --deployed` lit le compte comme `ff export` le lit et nomme, une ligne chacun, ce qu'un départ doit changer et que le code ne montre pas : une fonction qui reçoit l'événement d'origine de FF, ou dont le nom sort de la règle de Lambda ; une fonction gardée chaude, ce qu'AWS facture comme de la concurrence provisionnée ; une adresse qui prend les clés d'API de FF, là où AWS demande une requête signée avec les clés d'AWS ; un domaine sur une adresse ou un site, qui passe derrière CloudFront ; une fonction dont la clé a utilisé le S3, le SQS ou le SES de FF, d'après les usages quotidiens de sa clé ; et, pour un propriétaire, les clés de stockage du compte, avec leur dernier usage. Chacun est un avertissement : avec `--strict`, la commande échoue tant que quelque chose pointe vers FF, la dernière étape d'un départ.

**De retour sur FF, dans un autre compte :** le modèle se déploie sur FF aussi, comme `sam deploy` le prend : `ff deploy template.yaml --stack-name <pile> --parameter-overrides <nom>=<valeur> …` dans le dossier crée les mêmes fonctions, avec leur code, leurs variables et leurs adresses, les mêmes files et les mêmes compartiments, ce que la suite de tests de `ff` vérifie par l'API de FF. Donnez au paramètre de chaque compartiment un nom à vous, le nom d'un compartiment étant unique dans tout FF, et les valeurs de `secrets.template.env` : un secret revient en variable, Lambda n'ayant rien d'autre ; pour qu'il reste un secret sur FF, retirez-le du modèle et donnez-le avec `ff secrets set`. Les planifications restent éteintes jusqu'à `ScheduleState=ENABLED`, et un alias qui nomme une version reste à part, comme le dit `MIGRATION.md`.

**Vérifiez avant de déployer :** `sam validate --lint --region <votre région>` dans le dossier ; avec Terraform, `tofu init && tofu validate` dans `terraform/`. Puis `MIGRATION.md`, étape par étape : les planifications restent éteintes chez AWS (`ScheduleState`, ou `schedule_state` dans `terraform.tfvars`) jusqu'à ce que celles de FF le soient, pour qu'aucune ne tourne des deux côtés, et FF sert chaque appelant jusqu'à son départ.
